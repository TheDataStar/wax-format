# DeltOS — Track G

Platform Services & Orchestration — Technical Refinement

*Working draft · September 2026 · seventh of eight per-track refinements, revised after independent technical review — see §13*

## 1. Scope

Track G owns the plumbing every self-hosted service — Track G's own G3-G7 and every Track H app still to come — actually runs on: how a service is described and kept alive (G1), how it's reached under one hostname with real TLS (G2), and a small set of fleet-internal utilities (G3-G5) plus automation/telemetry tooling (G6, G7) that exist specifically because a fleet of boxes with limited or shared bandwidth shouldn't each reach the open internet independently for the same thing. Five other tracks already reference G1, G2, G3/G4, or G6/G7 by name, several with an open question explicitly deferred to "once Track G's refinement exists" — settling those, not just describing G1-G7 in isolation, is this document's real job.

## 2. Service Orchestration (G1)

The master plan splits this by tier — Docker Compose with healthchecks on Pi-class hardware, K3s single-node or clustered on mini-PC/NUC — without saying whether that's one authoring format or two. Worth settling before either exists, since every Track G/H service depends on the answer.

- **One authoring format — and an honest statement of what translation does and doesn't cover:** Every Track G and Track H service is defined once, as a Docker Compose file with restart and healthcheck directives — the same artifact regardless of tier. On Pi-class hardware and a single mini-PC/NUC (the overwhelming majority of real deployments, per Track E's E6 table), Compose runs the service directly; a crashed container is caught by its own healthcheck and restarted automatically, which is what the master plan's requirement actually asks for and doesn't need a cluster to deliver. This deliberately forecloses, rather than merely clarifies, the master plan's other named option of a single-node K3s deployment — one authoring format for the common case was judged worth giving up that option, not an oversight. K3s is reserved for a genuinely multi-box, clustered Community Hub/Field Ops deployment — several physical mini-PCs pooled together — and Kompose is used only to scaffold the initial container/port/volume mapping from each Compose file, not as a complete, automatic translation: Kompose's healthcheck-to-probe and restart-policy conversion is partial, so liveness/readiness probes and restart behavior are hand-specified on the Kubernetes side for each service rather than trusted to translate correctly. More importantly, Kompose does not provide shared or distributed storage — a stateful service (Gitea's SQLite database, §4; Node-RED's saved flows, §7; Prometheus's own time-series data, §8) is pinned to whichever single physical node it was first scheduled on via node affinity, not treated as freely reschedulable across the cluster. The cluster genuinely helps distribute stateless load; it does not give these specific services real high availability, and this document says so rather than implying Kompose translation solves that.
- **Scope split with Track F's F4, stated rather than assumed:** Track F's F4 (Track F §4) installs and updates content — .wax packs and their manifests — through its own verify/fetch/place/register pipeline. G1 orchestrates services: long-running, independently-addressable processes like G3-G7 and Track H's self-hosted apps. A content pack's own companion process (Track B's B3 runtime_ram_bytes note names the example of a model runtime co-located with one specific pack) stays a deltos-shelld-launched process alongside its wax-serve instance (Track C §5) — the same way wax-serve itself is launched — not a G1-orchestrated service, since it's scoped to one pack's lifecycle rather than being a standalone service other components address independently.
- **Data volumes, confirmed against Track E's storage convention:** Every service's persistent data lives under its own subdirectory of /var/lib/deltos/ (Track E §4), matching the single-backup-boundary convention Track F's F10 already assumes it covers (Track F §9). G1's compose files mount volumes there specifically, never to a path Compose would otherwise default to outside that tree.
- **Health status feeds Track F — a requirement flowing backward, confirmed there:** G1 exposes each service's current health — the same signal already driving auto-restart — over a small local read API, intended for Track F's deltos-healthd (Track F §6) to poll alongside its own OS-level metrics, so F1's admin console shows one unified health picture rather than an admin needing two different tools to answer "is everything actually running." Track F's own document, drafted before G1's health API existed to poll, doesn't name this input — a companion amendment confirms it there (Track F §19) rather than this document silently asserting an integration the other side hasn't agreed to.
- **Container-image-tag versioning, actually specified:** Track E credits G1 with the installable-stack path's update/rollback mechanism (Track E §3's amendment) without this document previously saying how it works. Specified here: each service's compose file pins an explicit image tag, never :latest; an update pulls and health-checks the new tag before rewriting the pin, and the previous tag is retained, unpruned, for a stated minimum of the last two versions. Rollback is an admin-triggered action (from F1, Track F §5) that re-points the pin at a retained prior tag and restarts the service — a real, if manual, mechanism, not merely a named concept.

## 3. Reverse Proxy & Ingress (G2)

The most load-bearing single component in the plan, per the master plan's own assessment — nearly every Track G/H service, F1, F6, and eventually F12 all sit behind it. Worth being concrete about what "one hostname" and "automatic internal TLS" actually mean before Track H's service count grows past a handful.

- **Caddy, for a stated reason:** Caddy over Traefik specifically because its automatic-TLS mode has a genuinely zero-config path for an internal, non-public-CA case: Track E's E10 already established deltos.lan as a private, non-internet-resolvable suffix (Track E §14), and a box with no public DNS record and no open port 80 to the internet could never complete an external ACME challenge anyway. Caddy's internal-CA mode issues and rotates certificates for every proxied hostname locally instead.
- **Hostname scheme — settling Track E's own open item:** Track E's E10 flagged the specific hostnames under deltos.lan as "still Track G's G2 to settle jointly" (Track E §17). Settled here: each platform service gets a fixed, predictable subdomain — admin.deltos.lan (Track F's F1), git.deltos.lan (§4), registry.deltos.lan (§5), flows.deltos.lan (§7), metrics.deltos.lan (§8) — with Track H's future services expected to follow the same one-service-one-subdomain pattern rather than each inventing its own naming. Resolution needs a DNS record, not just a naming convention: Track E's CoreDNS zone (Track E §14) carries one wildcard record, *.deltos.lan, pointed at G2's own address — a client's query for any of these subdomains resolves the same way without a per-hostname entry needing to be added by hand each time a service is added.
- **Resolving Track C's own open question — per-pack origins move to hostnames:** Track C's C4/C5 flagged, as an open decision, whether per-(pack, profile-slot) origins (Track C §5) should stay as 127.0.0.1 ports or move to distinct hostnames behind G2 once G2 existed (Track C §13). Answered now: a wildcard subdomain pattern — pack-<pack_index>-slot-<profile_slot>.deltos.lan — covered by the same wildcard internal certificate as above, so a fleet of packs and profile slots doesn't require registering a hostname per combination by hand. This becomes available once G2 lands (P2, §11); Track C's existing port-based scheme remains correct and necessary before then, and this document doesn't force an earlier migration than Track C's own phase timing calls for.
- **TLS bootstrapping supersedes, rather than duplicates, Track F's pre-G2 workaround:** Track F's F1 stated a locally-generated self-signed certificate as its pre-G2 baseline (Track F §5), specifically because nothing existed yet to do this properly. Once G2 lands, F1 — like every other proxied service — is issued a certificate from G2's own internal CA instead. This retires only the certificate half of F1's bootstrapping; F1's login itself keeps authenticating against deltos-identityd's password_hash (Track F §3) until F12 lands at P4 — G2 is a precondition for F12, not a substitute for it, and §12 below is corrected to say so rather than implying both retire together.
- **Trusting G2's own CA — an enrollment step, not an assumed outcome:** A device only stops seeing a certificate warning once it has actually installed G2's internal CA root, and nothing installs that automatically. Concretely: the CA root is downloadable from F1's admin console (Track F §5) for any device an admin sets up deliberately, and offered as a QR code on F2's very first-boot screen (Track F §2) for the first admin device specifically, before F1 is even reachable. A device that never installs it — a visitor's own laptop, a BYOD device — still connects and still gets working TLS encryption, just with a browser warning it has to click through; that's a stated, accepted limitation for unenrolled devices, not a gap this document pretends away.
- **Gating third-party services that don't know about deltos-identityd:** Gitea (§4) and Node-RED (§7) both ship their own independent login systems with no native way to check a request against F1's session or deltos-identityd's query_role — reusing F1's "pattern" in name only would leave each with its own separate, unintegrated account database, exactly the second-auth-story problem Track F's F1 was designed to avoid. The actual mechanism: Caddy's forward_auth directive checks every request to git.deltos.lan and flows.deltos.lan against a small local endpoint that validates the caller's F1 session cookie (and, for flows.deltos.lan, that the associated profile's role is admin, via identityd's query_role) before proxying to the backend at all. Gitea's and Node-RED's own built-in login screens are disabled — each runs behind G2 under one shared internal service account — so G2's forward-auth check is the actual access gate, not a second, independent one a request could reach around.
- **A fleet content-cache mode, designed properly — corrects both a cross-track misattribution and this document's own first-draft oversimplification:** Track B's B4↔B13 catalog-sync design (Track B §5) named "Track G's G3/G4 for fleet-internal mirroring" of pack downloads; G3 is source-code hosting and G4 is a container-image registry, and neither caches arbitrary HTTP downloads (corrected in a companion note to Track B, §18). But the first draft of this section then asserted G2's own reverse-proxy role could do this "as is," which doesn't hold up: a reverse proxy fronts inbound traffic to services behind it, while caching *other* boxes' *outbound* fetches to an external service (B13) is a forward/caching-proxy function — a different capability Caddy doesn't ship by default, and one that needs those other boxes' fetch traffic actually routed through the cache box in the first place, which nothing named. The corrected design: an admin-designated box (paired via Track F's F6, Track F §7) runs Caddy built with a caching module (via xcaddy, e.g. caddy-cache or souin) rather than the stock binary every other box uses. Other fleet members' B4/F4 fetch clients (Track F §4) are configured, once paired to a cache box, to route their B13 fetches through that box's LAN address — discovered via the same Avahi/mDNS same-LAN mechanism Track E's E9/E10 already use for fleet discovery — falling back to a direct fetch if the cache box is unreachable. This is a genuinely separate build and configuration surface from G2's baseline ingress role, not a free side effect of it; it also creates a new requirement on Track F's F4 (an upstream-override option) that Track F's own document didn't anticipate — flagged and confirmed there (Track F §19).

## 4. Local Git Service (G3)

Gitea (or its Forgejo fork), SQLite-backed — worth one concrete scope decision, since Track F's F8 already hosts the project's own public governance repositories on GitHub (Track F §12) and G3 shouldn't be read as a second copy of that.

- **Scope: organization-local, not project-public:** G3 exists for what one deployment (a school, a community hub) wants to version-control for itself — custom content-authoring work, local configuration-as-code, a class's own project repositories — not as a mirror or replacement for the public wax-format/DeltOS repositories Track F's F8 already names externally (Track F §12). A box or fleet that wants to contribute upstream still goes through those public repos, not through its own G3 instance.
- **Access:** Fed via the browser (master plan) means Gitea's own web UI, reached at git.deltos.lan behind G2 (§3). G3 is tagged P4 (§11), strictly after G2's P2 landing, so it never runs without G2 available — access is gated by G2's forward-auth check (§3's mechanism) from the start, not a bootstrapped fallback that later gets replaced. Gitea's own login system is disabled; a request that hasn't already passed G2's auth check never reaches it.

## 5. Local Container Registry (G4)

A lightweight OCI registry for fleet-wide image distribution with no internet, per the master plan — this is what lets a fleet of boxes update G1's own service images without every box independently reaching the public internet.

- **What it distributes:** G4 mirrors the container images G1's compose files reference — Track G's own G3, G5, G6, G7, plus Track H's forthcoming self-hosted apps. One box (or an admin-designated fleet member, the same F6-paired mechanism as G2's cache mode, §3) pulls a new image once from its public registry, and every other fleet box pulls from G4 instead. It does not distribute WAX content packs — that remains B13/G2's job (§3's correction) — G4's scope is strictly container images for Track G/H's own software.
- **Access control, stated rather than left implicit:** A stock OCI registry has no authentication by default, and Track E already established that Community Hub/Field Ops hardware often runs on shared or semi-public networks (libraries, community centers) — an open G4 would let any device on that network push an arbitrary image for G1 to later run as a live service, a distinct and more basic problem than provenance (below). G4 requires HTTP Basic Auth for both push and pull; its credential is generated at G4's own setup and distributed to fleet members through Track F's F6 pairing exchange (Track F §7's per-peer shared-secret pattern, reused here rather than inventing a third credential-distribution mechanism).
- **Image provenance, flagged rather than solved:** Track F's F7 (Track F §8) established a signing story for WAX packs specifically; nothing here provides an equivalent for container images. Verifying that an image pulled through G4 actually matches what its upstream publisher built (image signing, e.g. cosign, or at minimum digest-pinning rather than trusting a mutable tag) is flagged as an open decision (§10) at the same scale as F7's own deferred TUF work — not assumed solved by G4's existence, and distinct from the access-control question above: access control says who may push; provenance says whether a pushed image is what it claims to be.

## 6. Apt-Cacher / Package Caching (G5)

apt-cacher-ng, per the master plan — worth being clear about which deployment path this actually helps, since the two OS paths Track E now supports (Track E §21) don't both use apt.

- **Installable-stack path only, stated plainly:** G5 caches Debian/Ubuntu apt packages — directly useful on the installable-stack path (Track E §2's Debian/Ubuntu-family target). It does nothing for the appliance-image path's own OS updates, which flow through Track E's ostree channel entirely outside apt (Track E §3) — G5 is not a second update mechanism for that path, only a package cache for whatever on the box does use apt. It also helps the one Track G/H build scenario that pulls apt packages directly: a service without a suitable pre-built image, built from source locally rather than pulled through G4 (§5) — the uncommon case, since G4's whole purpose (§5) is to avoid exactly this by mirroring pre-built images instead.

## 7. Visual Flow-Automation Engine (G6)

Node-RED (or equivalent), driving E15's smart-grid automation and reacting to whatever's published on Track E's shared MQTT bus (Track E §11) — the master plan is explicit that this includes triggering physical alerts, which deserves the same care Track E gave the bus itself.

- **Authenticated onto the bus — the integration Track E deferred, done here:** Track E's own minimum posture (Track E §11) was stated as a floor, not a finished design — "bind to localhost/VPN-only where possible, or require username-plus-per-topic ACLs otherwise... full policy design can wait for G-track integration." That integration happens here, and it needs to go further than the passive publish-only bridges (E12/E15) that posture was originally written for: G6 is a bidirectional client with a materially more sensitive access pattern — broad subscribe (it needs to see readings across device classes to automate against them) alongside narrow, scoped publish (it should only be able to write to a reserved alert/action topic prefix, e.g. deltos/v1/actions/#, never masquerade as a sensor). G6 gets its own dedicated Mosquitto credential with exactly that asymmetric ACL — full subscribe, publish restricted to the actions prefix — rather than reusing E12/E15's publish-only bridge credential or an unscoped admin one.
- **Editing flows is admin-only — enforced by G2, not by Node-RED itself:** G6's flow editor — the surface that can wire a sensor reading to a physical alert — needs to be admin-only the same way F6 and F13 already are, but Node-RED's own built-in adminAuth is a static username/password list in settings.js with no native integration to F3's role model. Rather than leave that as an unenforceable analogy, flows.deltos.lan sits behind G2's forward-auth gate (§3's mechanism), which checks the caller's role via identityd's query_role before proxying to Node-RED at all; Node-RED's own login screen is disabled, matching how §4 gates Gitea the same way.
- **Exposure, simplified by G6's own phase timing:** G6 is tagged P4 (§11), strictly after G2's P2 landing, so — unlike F1, which can launch in the same phase as G2 and genuinely needs a pre-G2 fallback (Track F §5) — G6 never runs without G2 already in place. It gets a proper internal-CA certificate at flows.deltos.lan from the start; no self-signed-certificate fallback is needed or specified, since the situation it would cover never occurs.

## 8. Metrics & Dashboard Stack (G7)

Prometheus/VictoriaMetrics plus Grafana, per the master plan — needs a stated boundary against Track F's F5 (deltos-healthd), or the project ends up with two overlapping ideas of "how healthy is this box."

- **Division of labor with Track F's F5:** F5 (Track F §6) is a lightweight, always-on, every-tier health snapshot — coarse retention, SQLite-backed, feeding F1's admin console and F6's fleet view with "is this box OK right now and recently." G7 is a Community Hub/Field Ops-only, opt-in, long-retention time-series stack for genuinely rich telemetry — E9's solar data and E12/E13/E15's sensor and smart-grid readings — and can optionally scrape F5's own metrics as one more source for a deployment that wants deeper history than F5's short window keeps. Kiosk and Classroom-tier boxes never run G7 at all; F5 alone covers them, matching how Track E already scopes E8/E9/E12-E15 to Community Hub/Field Ops (Track E §16).
- **What it consumes:** G7 scrapes a small, stated MQTT-to-metrics bridge — an exporter subscribing to Track E's bus and re-publishing as Prometheus-scrapeable series — rather than subscribing to MQTT directly itself. This keeps "who talks to the broker" to the same small, authenticated set §7 already establishes for G6, instead of adding G7 as a second MQTT client with its own credential to manage.

## 9. Hardware & Profile Scoping

- G1 and G2 apply to every deployment that runs any self-hosted service at all, from Classroom profile upward — a single-reader Kiosk box with no admin services running has nothing for either to orchestrate or front, and both stay dormant or uninstalled there rather than adding to Track E's already-flagged Kiosk-tier budget concern (Track E §22).
- G3, G4, and G5 matter once a fleet exists to actually benefit from local mirroring or caching — a single isolated box gains little from any of the three, since there's no second box to mirror to or share a cache with.
- G6 and G7 are Community Hub/Field Ops-scale concerns exactly as Track E already scoped E8, E9, and E12-E15 (Track E §16) — there's no automation to wire or telemetry to graph on hardware that never turns those sensors on.

## 10. Open Decisions Needed Before Implementation

- Decide G4's image-provenance mechanism (§5) — access control is now specified, but this document states the provenance gap, matching Track F's F7 honesty about its own v0.9 limits, without resolving it here.
- Confirm with Track H, once it exists, that G1's one-Compose-file-per-service convention (§2) is what Track H's own service definitions actually assume, rather than Track H inventing a second convention independently.
- Confirm whether the catalog-index sync itself (as distinct from a discrete pack install) actually routes through F4's stage-2 verification (Track F §4) when fetched via §3's fleet-cache mode — Track F's F4 already commits to re-verifying regardless of source for installs, but whether the catalog-index pull is treated the same way isn't yet confirmed.
- Decide whether K3s cluster provisioning (§2) is itself a Track G deliverable or belongs with Track E's E7 provisioning tool (Track E §8), since both touch "how new hardware joins something larger."
- Settle G6 and G7's own resource footprint against Track E's Community Hub tier budget (mini_pc, 16GB floor) — Track E's own §5/§17/§22 already flags that budget as unvalidated; G6 and G7 are two more concurrent processes it needs to include.

## 12. What This Unblocks

- Every future Track H service gets one settled orchestration convention (§2) and one ingress/TLS/hostname scheme (§3) to build against, instead of each service inventing its own deployment mechanics.
- Track F's F12 (SSO) gets an actual reverse proxy to sit in front of (§3); F1's pre-G2 certificate bootstrapping (Track F §5) retires once G2 lands, while its password_hash-based login (Track F §3) keeps its own stated retirement path at F12/P4 — the two are corrected here to retire on separate schedules, not together.
- Track C's C4/C5 open question about ports versus hostnames (Track C §13) gets answered (§3), and Track E's E10 open item about specific deltos.lan hostnames (Track E §17) gets settled.
- Track E's installable-stack update story (Track E §3's amendment) gets an actual mechanism — G1's container-image-tag versioning — instead of a named-but-undesigned concept.
- Track B's B4↔B13 fleet-mirroring reference gets corrected to an actual, buildable mechanism (§3) instead of pointing at two components that were never built for it.

## 13. Independent Review — Findings and Resolutions

- **[Critical]** The fleet-cache mode conflated a reverse proxy with a forward/caching proxy — Caddy doesn't ship HTTP response caching by default, and nothing specified how other fleet boxes' fetch traffic would actually route through the designated cache box. "Using G2's own reverse-proxy role rather than a new component" wasn't accurate. Resolved: specified as a distinct build (Caddy plus a caching module via xcaddy) with an explicit routing mechanism (F4's fetcher configured with an upstream override once paired, discovered via Avahi/mDNS) — a genuinely separate surface from G2's baseline role, not a free side effect of it, with a new requirement flowed to and confirmed in Track F (§3, Track F §19).
- **[Critical]** The "one Compose file, translated via Kompose" claim glossed over real gaps exactly where K3s is used: Kompose's healthcheck/restart translation is partial, and it provides no shared or distributed storage — meaning the one deployment shape K3s exists for (genuine multi-box clustering) couldn't actually give stateful services real high availability the way the original phrasing implied. Resolved: Kompose scoped to initial scaffolding only, not full translation; stateful services pinned to one node via affinity, stated honestly as not gaining HA from the cluster (§2).
- **[Critical]** G1 was tagged P3 while the master plan tags H2 (media server, Track G's first real consumer) at P2 — H2 would have nothing to orchestrate under it at the phase it's committed to ship, a cross-track ordering conflict this document's own §1 frames as exactly its job to catch. Resolved: G1 moved to P2 alongside G2's baseline function, with the master plan's own G1 tag corrected to match (§2, §11).
- **[Security]** G4 had no stated access-control model — a stock OCI registry allows anonymous push/pull by default, and Community Hub/Field Ops hardware often runs on shared or semi-public networks, making an open G4 a path for any device on the network to push an image G1 later runs as a live service. Resolved: HTTP Basic Auth required for both push and pull, credential distributed via Track F's F6 pairing exchange (§5).
- **[Security]** G3 and G6's claimed reuse of "Track F's F1-style pattern" didn't specify how a third-party service with its own independent login system (Gitea, Node-RED) would actually check a request against F1's session or F3's role model — an analogy, not a mechanism, leaving each with an unintegrated, separate account database in practice. Resolved: both gated by G2's own forward-auth check against identityd's session/role state, with each service's own built-in login disabled (§3, §4, §7).
- **[Security]** G6's MQTT authentication claim asserted Track E's stated minimum posture as already sufficient, when Track E explicitly deferred "full policy design" to this exact integration and wrote that posture with passive, publish-only bridges in mind — not a bidirectional, potentially alert-triggering client like G6. Resolved: G6 given its own dedicated credential with an asymmetric ACL (broad subscribe, publish restricted to a reserved actions topic prefix), the integration work Track E actually asked for rather than an assumption that it was already done (§7).
- **[Moderate]** §2 asserted Track F's deltos-healthd already polls G1's health API, but Track F's own document — drafted before G1's API existed — never names this input, an unconfirmed one-sided cross-track claim of exactly the kind this document corrects elsewhere. Resolved: framed as a requirement flowing to Track F, confirmed there by a companion amendment (§2, Track F §19).
- **[Moderate]** §12 stated G2 gives F1's entire pre-F12 bootstrapping (both its certificate and its login) a retirement path once G2 lands — but Track F is explicit that the login bootstrap retires only once F12 itself exists, at P4, two phases later. Resolved: TLS and login retirement corrected to their actual separate schedules (§3, §12).
- **[Moderate]** §10's fleet-cache trust-boundary question was framed as fully open, when Track F's F4 already commits to re-verifying signature and rollback state regardless of source for any install — that half of the question is already settled by existing, committed design. Resolved: narrowed to the genuinely open part — whether the catalog-index sync itself, as distinct from a discrete pack install, is confirmed to route through the same verification (§10).
- **[Moderate]** The fleet-cache submode was presented as part of a flat P2 deliverable alongside the rest of G2, despite depending on Track F's F6 (P3) to designate and pair a cache box — not actually usable at G2's own landing. Resolved: split into its own P3 phase-table line, distinct from G2's P2 baseline (§11).
- **[Moderate]** G6's stated pre-G2 self-signed-certificate fallback described a situation that, per this document's own phase table, never occurs — G6 lands at P4, strictly after G2's P2, unlike F1 which can genuinely launch alongside G2 and needs the fallback Track F specified. Resolved: removed for G6, replaced with a plain statement that it always has a G2-issued certificate from the start (§7).
- **[Moderate]** §12 credited G1 with "an actual mechanism" for Track E's installable-stack rollback story without this document ever specifying one. Resolved: image-tag pinning, retention of the last two versions, and an admin-triggered rollback action actually specified (§2).
- **[Moderate]** §2's choice to run Compose directly even on a single mini-PC/NUC silently overrode the master plan's separately-named "single-node K3s" option rather than flagging that it was doing so. Resolved: stated explicitly as a deliberate override, with the reason given (§2).
- **[Minor]** G5's stated apt-package-build use case didn't connect to any build process this document otherwise describes, which only covers pulling pre-built images. Resolved: connected to the one scenario where it applies — a service built from source locally rather than pulled through G4 (§6).
- **[Minor]** The wildcard hostname scheme named deltos.lan but never stated the actual DNS record that makes it resolve. Resolved: a wildcard record in Track E's CoreDNS zone, named explicitly (§3).
- **[Minor]** Nothing described how G2's internal CA root actually reaches and gets trusted by client devices — "the admin trusts one CA once" asserted an outcome with no enrollment step. Resolved: a download from F1 and a first-boot QR code specified, with the residual limitation for unenrolled devices stated rather than assumed away (§3).
