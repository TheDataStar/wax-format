# DeltOS — Track F

Admin, Identity & Fleet — Technical Refinement

*Working draft · September 2026 · sixth of eight per-track refinements, revised after independent technical review (§18) and cross-track amendments from Track G's design (§19), Track H's review (§20), UX/design-language research (§21), and product direction on Guest access (§22)*

## 1. Scope

Track F owns everything an operator — not a learner — touches: how a box secures itself the moment it's first powered on (F2), who is allowed to do what on it and what a learner identity actually is (F3, F11), how content and updates actually get onto a running box regardless of who or what triggered it (F4), how an admin watches over and manages one box or many (F1, F5, F6), how the trust the rest of the project already assumes (a signed pack, a trusted catalog) is actually protected (F7), how a box's data survives a hardware swap (F10), and the project's own governance and documentation (F8, F9). Five other tracks already reference F3, F4, F6, F10, F11, and F12 by name without this track ever having said what those actually are — closing that gap is this document's first job, the same role Track E's E6 table played for hardware-tier vocabulary.

## 2. First-Boot Security (F2)

The master plan states the requirement plainly — force a unique generated admin password before the box does anything else — but not how that password reaches the admin on a box that may never have touched a network, or what exactly stays locked until it's set.

- **Generation and disclosure:** On first boot, deltos-shelld generates a high-entropy random password — not a static default, not a weak PIN — and displays it exactly once, full-screen, as both plaintext and a scannable QR code (for an admin without a keyboard handy), with an explicit "I've saved this" confirmation required before the box proceeds. There is no email or SMS step available at this stage — the box may have no network path yet — so this on-screen disclosure is the only channel, and the screen says so plainly: this is the one chance to see it before only its hash is kept.
- **What stays locked until this completes:** No role-gated deltos-shelld operation — install_pack, remove_pack, mount_removable, join_network, configure_ap, the same set Track C's C1 and Track E's E3 amendment both check against F3 (Track C §2, Track E §6) — executes until F2 has completed and exactly one profile exists with the admin role (§3). Track C's C10 onboarding wizard wraps this step as its literal first screen (Track C §10) rather than duplicating it.
- **Identical regardless of deployment path:** Whether the box arrived via the appliance-image path or the installable-stack path (Track E §2, §21), F2's flow is the same, because it lives in deltos-shelld — a DeltOS component, not an OS-layer script. This is a direct instance of the product direction that DeltOS itself, not the underlying OS, carries the heavy lifting (Track E §21).

## 3. Identity, Roles & Progress Data (F3, F11)

The master plan lists F3 (user/role management) and F11 (identity & progress data model) as separate line items, but Track C's own review already showed they're one data problem seen from two angles — F11 is "who exists," F3 is "what can they do" — and both need answering by the same privileged caller through the same kind of narrow local IPC Track C already established for everything else deltos-shelld exposes.

- **One local service: deltos-identityd:** F3 and F11 are implemented as a single privileged local daemon, SQLite-backed (matching the project's service-selection filter), storing its database under /var/lib/deltos/identity/ per Track E's storage convention (Track E §4). It owns two tables: profiles (profile_id, display_name, role, class_or_group, profile_slot, password_hash, created_at) and progress_events (profile_id, pack_id, event_source, event_type, timestamp, payload) — exactly the shape Track C's C8 assumed it would need (Track C §8), now confirmed rather than left an assumption. The event_source column (added per §20) discriminates which ID namespace pack_id is drawn from, since more than one producer writes into this table (§20).
- **Credential storage, added after review:** profiles carries its own password_hash column (Argon2id) — the actual gap the first draft left open: F2 (§2) and F1's login (§5) both refer to "the admin credential" without anywhere to store or look one up. Each profile with the admin (or, once created, teacher) role authenticates with its own password against its own hash, not a single box-wide secret shared by every admin. F2's first-boot flow seeds the very first admin profile's password_hash from its generated password; any additional admin or teacher profile created later through F1 gets its password set explicitly by the creating admin at creation time, not auto-generated. Student profiles are the exception to this column being required — see §21's passwordless-student amendment.
- **profile_slot answers Track C's C5 dependency:** Track C's C5 needs a small, bounded, stable-for-life slot number per profile to key its per-(pack, profile-slot) browser origins (Track C §5). deltos-identityd assigns profile_slot at profile creation from a bounded pool per device (0–31, matching the range Track C's design already assumed) and never reassigns a slot while its profile exists — a freed slot is only reused once Track C's storage-wipe-on-reuse step has actually run for it (Track C §5's post-review amendment). Exhausting the pool (a 33rd concurrent profile on one device) is a hard stop, not a silent failure: profile creation refuses with an explicit "free a slot first" message in F1/C5's UI rather than wrapping around or reusing a live slot. Whether 32 is enough for a real multi-class rotation is flagged as an open decision (§15), not assumed settled by picking a round number.
- **The three IPC calls deltos-shelld and its callers actually need:** query_role(profile_id) -> {admin, teacher, student, none} answers the exact dependency Track C's C1 flagged as needing confirmation (Track C §13) and the call Track E's E3 amendment relies on for Wi-Fi role-gating (Track E §6). list_profiles(device) -> [{profile_id, display_name, profile_slot}] is the second call Track C's C5 explicitly asked for — "a stable profile_id and a 'list profiles for this device' call" (Track C §6) — missing from the first draft's enumeration entirely. Both are read-only and narrow; nothing about a profile's role or credential is exposed beyond what each call's own name promises.
- **Caller authentication on identityd's own socket, added after review:** identityd is reachable by more than one kind of caller — deltos-shelld (the two calls above), F1's admin-authenticated requests (profile/role management, credential resets), and whatever serves C8's read-only progress call — which is exactly the multi-caller pattern Track C's own review treated as security-critical for deltos-shelld's socket (Track C §2's Origin-allowlist-plus-capability-token fix). identityd applies the same category of control: peer-credential checks (SO_PEERCRED) restrict the socket to a fixed allowlist of local binaries, and each caller is further scoped to only the calls its role needs — deltos-shelld gets query_role/list_profiles only, never raw profile writes; C8's progress reader is scoped to one class_or_group per request, sourced from the teacher's own authenticated F1 session, not a caller-supplied parameter it could widen itself.
- **Progress events, exposed read-only and scoped:** Track C's C8 (coach dashboard) reads progress_events through a read-only IPC call scoped to a teacher's own class_or_group — never raw SQLite access to deltos-identityd's database file. This keeps F11's schema free to evolve without breaking every consumer's assumptions about column layout, and keeps a teacher's dashboard from ever seeing another class's data by construction rather than by application-level filtering alone. C8's read now also returns each row's event_source, so the dashboard can render a WAX-pack completion and a Kolibri lesson completion as what they actually are rather than silently conflating two different kinds of progress under one label (§20).
- **Who can do what — the concrete permission set the master plan left unstated:** "Admin, teacher, student roles" names three roles without saying what separates them. Settled here:

| **Operation** | **Admin** | **Teacher** | **Student** |
|---|---|---|---|
| install_pack / remove_pack (Track C C1) | Yes | No | No |
| mount_removable (Track C C1) | Yes | No | No |
| join_network / configure_ap (Track E E3) | Yes | No | No |
| create/manage profiles in own class (F3/F11) | Yes | Yes | No |
| view progress across own class (Track C C8) | Yes | Yes | No |
| view own progress only (Track C C8) | Yes | Yes | Yes |
| F1 admin console access (§5) | Yes | No | No |
| F6 fleet pairing / F13 vault access (§7, §11) | Yes | No | No |

- **Teacher's surface stays in-shell, deliberately:** A teacher gets class-scoped profile management and C8's dashboard, both reached through Track C's shell (Track C §8) — never F1's server-admin console (§5), F6's fleet tooling, or F4's install pipeline directly. This keeps the blast radius of a compromised or careless teacher account limited to their own class, not the box's system configuration or its content pipeline.
- **F11's owner decided now, ahead of the master plan's own P2 target:** The master plan only committed to deciding F11's owner by P2 (master plan §5); this document settles the design itself here, in Track F's own initial draft — ahead of, not merely on, that schedule. Track C's C8 had provisionally slotted itself at P3 contingent on F11 landing in time, with an explicit note that the tag would need revisiting if Track F slipped (Track C §8, §14). With F11 designed here, that contingency resolves — see §16's phase table, and the confirmation added to Track C's document (Track C §20).

## 4. Install / Update Pipeline (F4)

F4 is the single mechanism three different callers already assume exists — Track C's C6 and C7 both terminate in it (Track C §7), and Track E's E7 provisioning tool pre-seeds installs at flash or install time (Track E §8, §21). Getting it right once here matters more than almost anything else in this document, since every other track's install story is downstream of it.

- **A distinct privileged daemon, not shell-embedded logic:** F4 is its own local daemon, deltos-installd, rather than logic embedded inside deltos-shelld — a persistent but idle-when-empty process (no polling loop running when its queue is empty), a deliberately small footprint on the Kiosk-tier budget this document's own §14 flags. deltos-shelld's install_pack/remove_pack IPC calls (Track C §2) forward to it; F1's admin console (§5) calls it directly for bulk or remote operations. One pipeline serves both callers instead of two separate, slowly-diverging implementations of "verify, fetch, place, register."
- **Starter packs don't go through F4 at all — corrected after review:** The first draft credited E7's provisioning tool with pre-seeding pack installs pre-boot; Track E's own E7 design pre-seeds only Wi-Fi credentials and Deployment Profile selection (Track E §8), never content. Track B's starter-pack set (Track B §7's B5 proposal) is instead baked directly into the OS image (appliance path) or the installer package (installable-stack path, §8 below) at build time — already present in /var/lib/deltos/packs/ and registered in B4 the first time deltos-identityd and B4 exist to read them, with no F4 fetch involved. F4's pipeline is exercised the first time anything is installed or updated after that initial state, not before deltos-shell is even running.
- **The pipeline's four stages, the same for every caller:** (1) Fetch the manifest and .wax bytes — a catalog-index-driven download (Track B §5) or a mounted USB path or peer address (Track C §7). (2) Verify signature against B13's project key (Track A A7, §8 below) and apply the highest-archive_uuid+version-seen rollback check (Track A §6) — regardless of source, per Track C's own C7 review finding (Track C §7). Both checks are mandatory from the same point Track A now enforces them by default — P2, per Track A's own post-review correction (Track A §14) — not merely from whenever F4 itself first runs. (3) Write to a temporary path under /var/lib/deltos/packs/ and atomically rename into place only once fully written and verified, so B4 never sees a partially-downloaded pack. (4) Register or update the corresponding row in B4's catalog and emit the change notification Track C's C2 subscribes to (Track C §2).
- **Resumable and queued, the two adjectives the master plan actually asked for:** Fetches use HTTP range requests against B13's distribution (Track B §5), so a large multi-GB pack — the realistic case on Kiosk-tier's slower uplinks — survives a dropped connection and resumes from its last confirmed byte range rather than restarting. Requests queue by default (one active fetch at a time per box) rather than run concurrently, since Kiosk/Classroom-tier hardware's constrained bandwidth and storage I/O — a distinct concern from, and additional to, Track E's own flagged RAM budget (Track E §5) — are more likely to have parallel installs starve each other than finish faster.
- **Role-gating happens here too, not only at the IPC layer:** Track C's C1 already checks a caller's role before forwarding install_pack/remove_pack over IPC (Track C §2), but F1's admin console calls F4 directly (§5, above), bypassing that check entirely. F4 re-verifies role independently for any caller that doesn't arrive through deltos-shelld's IPC — the same defense-in-depth reasoning behind Track C's own Origin-allowlist-plus-capability-token pattern (Track C §2), not a weaker guarantee just because a caller is presumed already trusted.

## 5. Admin Console (F1)

One unified, wizard-driven web UI, per the master plan — this section decides where it runs, how it's reached, and how it authenticates before F12's SSO exists to front it.

- **What it's built from:** F1 is a server-rendered local web app — not a kiosk-mode browser app like deltos-shell — reachable from any device on the box's network at a fixed local address, so an admin can manage a box from their own laptop or phone without needing physical access to the kiosk screen itself. It calls the same local services every other component already exposes rather than re-implementing them: E4's diagnostics API (Track E §7), F5's health data (§6), F4's install pipeline directly for bulk or remote operations (§4), and deltos-identityd's admin-scoped calls for F3/F11 management (§3).
- **Wizard-driven, not a flat settings page:** The master plan's "wizard-driven" framing applies to F1 itself, not only to C10's first-boot flow — an admin's major tasks (pairing a new box into the fleet, §7; reviewing and confirming a restore, §9; creating a profile with a role and credential, §3) are each a short guided step sequence with the consequential choice confirmed explicitly, rather than a grid of settings a first-time admin has to already understand. Routine, low-consequence views (health readouts, §6; install queue state, §4) stay as plain dashboards — the wizard pattern is reserved for actions that change something, not for everything F1 shows.
- **Exposure and hardening, added after review:** F1 sits on the same LAN Track E's classroom AP serves to student devices (Track E §6) — a materially different threat model from Track C's kiosk-only IPC surface, and one the first draft didn't account for. Before F12/G2 exist: F1 serves over a locally-generated, self-signed TLS certificate created at F2's first-boot step (§2) rather than plaintext HTTP, so credentials aren't sniffable in the clear on the shared LAN even though the certificate isn't yet chain-of-trust verifiable; its session cookie is Secure and HttpOnly; login attempts are rate-limited with a growing lockout window to blunt brute-forcing F2's generated password over the network; and F1 prompts the admin to set their own replacement password at first login rather than leaving the generated one as a standing credential indefinitely. A genuinely separate admin-only network segment — so student devices can't reach F1's address at all — would close this more completely, but requires Track E's E3 to support a second, non-classroom SSID or VLAN, which E3 doesn't currently describe; flagged as an open decision (§15) rather than assumed available.
- **Authentication before F12 exists:** F12 (Authelia-based SSO) is P4-tagged (master plan) and depends on Track G's forthcoming G2 reverse proxy, neither of which exists yet — F1 cannot wait until P4 to have a login screen. Before F12 lands, F1 authenticates each request against the requesting profile's own password_hash (§3) via a session cookie scoped to F1's own local origin, hardened as above. Once F12 exists, F1 sits behind it like every other Track H service (master plan's own stated design), and this direct-auth path is retired rather than left running in parallel as a standing bypass.
- **One console, either deployment path:** F1 doesn't distinguish between a box provisioned via the appliance-image path or the installable-stack path (Track E §2, §21) — both expose the same local services underneath, so the console is identical either way. The only deployment-path-aware admin surface is E7's provisioning tool itself (Track E §8), a separate, earlier-stage tool from F1.

## 6. Device Health Monitoring (F5)

Storage, uptime, temperature, connectivity, per the master plan. This needs an owner — something has to poll these — and a place to keep history, or F1's console and F6's fleet dashboard are both reading live-only numbers with nothing to show a trend against.

- **deltos-healthd, a small unprivileged poller:** A lightweight local service polls storage usage against /var/lib/deltos specifically (per Track E §5's wear-leveling flag, not just total disk), uptime, CPU temperature where the board exposes it, and E4's connectivity API (Track E §7) on a fixed interval, writing snapshots to its own SQLite table under /var/lib/deltos/health/. It only reads sensors and existing local read-only APIs — no privileged operation, so it never routes through deltos-shelld at all.
- **Retention, not an unbounded log:** Snapshots are kept at coarsening resolution — full resolution for roughly the last 48 hours, hourly rollups beyond that, capped at a stated retention window (e.g. 90 days, flagged as not yet final, §15) — so a multi-year deployment's own health history doesn't become one more contributor to the wear/storage concern Track E's §5 already raised.

## 7. Fleet Dashboard & Multi-Box Trust (F6)

A multi-box view for organizations only makes sense once F6 knows which boxes exist and how to reach them — that's most of this section's real content, not the dashboard UI itself.

- **Discovery matches Track E's own answer, not a separate mechanism:** Same-LAN boxes are discovered automatically via E10's Avahi/mDNS (Track E §14), exactly as Track E's own answer to Track D's D8 peer-discovery question already established (Track E §9). Cross-site boxes have no automatic discovery — an admin explicitly pairs them into the fleet by exchanging Yggdrasil addresses (Track E §9) — and F6 is where that pairing actually gets entered and stored, resolving what Track E's review left as "Track F's forthcoming F6" (Track E §9's finding).
- **Per-peer trust is an explicit flag, not a side effect of pairing:** Pairing a box into the fleet, same-LAN or cross-site, grants nothing beyond appearing in F6's list. Track D's D8 requires that opting a fleet into cross-box federated results feeding local RAG context be an explicit admin decision, never a default (Track D §9). F6 stores this as a separate per-peer boolean, federated_rag_trusted, off by default and distinct from pairing itself. Federated results stay visible and origin-labeled in plain search (Track D's default) regardless of this flag — the flag only controls whether they can additionally feed an Ask DeltOS answer's evidence.
- **Fleet auth before F12 exists:** Same timing gap as F1 (§5): F6 needs to call other boxes' F1/F5 APIs before Authelia-based SSO exists. Each pairing exchanges a per-peer shared secret at pairing time, alongside the Yggdrasil address, rather than waiting for F12 — the same bootstrapping approach §5 uses for F1's own login, applied per-peer instead of per-admin. This is retired in favor of F12-based cross-box auth once Track G's G2 and F12 land, not kept running as a permanent second auth path.
- **What F6 actually shows:** Per-box health (F5, §6), install/update queue state (F4, §4), and Deployment Profile/hardware tier (Track E §5) — enough for an organization managing several boxes to spot one that's gone stale (no recent check-in), low on storage, or running an outdated pack version, without physically visiting each box.

## 8. Signing & Key Management (F7)

B13's publishing pipeline and F4's install pipeline (§4) both already assume "the project key" exists and is checked correctly — nothing so far has said how that key is actually protected, generated, or rotated. Closing that gap, ahead of TUF at v2 (the master plan's own F7 tag), is this section's job.

- **A deliberately small v0.9 key story:** One minisign keypair, matching Track A's chosen signing scheme — a root/signing key kept offline, used only during B13's approved → signed step (Track B §5, §9) as a deliberate, human-or-CI-triggered action, never held by any always-on, network-reachable service. There is no separate online/offline key split at v0.9; that additional hierarchy is deferred to TUF at v2, matching the master plan's own tag, rather than half-building TUF's key model now.
- **How a box gets the public key in the first place — corrected per path after review:** A box needs to verify its very first pack install before it necessarily has any trusted network path to fetch a key from, so the public verification key ships embedded ahead of time, not fetched on first boot — but the two deployment paths (Track E §2, §21) don't share one artifact to embed it in. On the appliance-image path, it ships in the base OS image itself. On the installable-stack path, there is no DeltOS-managed OS image — Track E is explicit that host-level updates there are the person's own responsibility, entirely outside DeltOS's control (Track E §3's amendment) — so the key instead ships embedded in the installer package (§8's own artifact for that path), the one thing on that path DeltOS does control end to end.
- **Key rotation, per path:** A rotation is distributed as a signed announcement bundled into whatever channel each path's initial key already came from: Track E §3's ostree channel for the appliance path, and a new installer-package release fetched over HTTPS from B13's own infrastructure for the installable-stack path — with the box's currently-trusted key itself (not a third-party CA) verifying that release's signature, the same bootstrapping-of-trust pattern used to accept the very first key. Neither path routes a rotation through a host update mechanism DeltOS doesn't own, and neither treats a bare replacement file a running box picks up unauthenticated as sufficient.
- **Compromise response, stated honestly as partial:** If the signing key is compromised, device-side rollback protection (Track A §6's highest-version-seen tracking) still does not stop an attacker from signing a new malicious pack with a version number higher than anything a device has seen — an accepted v0.9 gap already flagged in Track A and deferred to TUF's proper key-compromise/revocation model at v2. F7's only v0.9-level mitigation is operational: keeping the signing key offline and used only at the one approved → signed step narrows the exposure window and the number of systems that could leak it — not a claim that the underlying gap is closed.

## 9. Backup & Restore (F10)

Track E's storage convention (Track E §4) already gives this exactly one tree to work with — /var/lib/deltos/ — which is what keeps this section short rather than a sprawling per-component backup matrix.

- **One backup boundary:** F10 snapshots /var/lib/deltos/ as a whole — B4's catalog and installed packs, deltos-identityd's profiles/progress data (§3), Track G's forthcoming per-service data volumes — to an admin-chosen target (a mounted USB drive or a network location) on a schedule or on demand from F1 (§5). Backups are encrypted at rest using a passphrase the admin sets at backup time, separate from any login credential — stated here as a requirement, not left fully open, given the tree includes profiles' password_hash values and children's progress data (§3); only the specific encryption format/library remains an open decision (§15).
- **Restore never runs before a box has its own identity — closes a first-draft sequencing gap:** F10 restore is only available from F1 (§5), and F1 only exists to log into once F2's first-boot flow (§2) has already produced its own admin profile — a freshly-provisioned box always completes its own throwaway F2 flow first, on either deployment path, exactly as any other new box would. Restoring a prior backup onto it is then an authenticated F1 action performed by that freshly-created admin, who reviews what the backup contains and confirms before it overwrites local state — never an unauthenticated step that runs earlier than F2, and never a silent overwrite of the identity the admin just created.
- **Restored packs are re-verified, not copied in raw — closes a first-draft integrity gap:** The first draft let restore write backed-up packs straight into /var/lib/deltos/packs/ with no check at all — meaning a compromised or substituted backup (the stated default target is a bare USB drive) could reintroduce tampered, previously-rejected, or stale content with none of F4's protections applied. Corrected: restore feeds each backed-up pack back through F4's own stage-2 verification (§4) exactly as if newly installed. A pack that fails signature or rollback verification is not restored — it's surfaced to the admin as a rejected item, not silently reinstated.
- **deltos-identityd's own restore, protected the only way v0.9 can:** identityd's database isn't a signed WAX pack, so it has no equivalent of F4's signature check available to it. The stated v0.9 mitigation is a human in the loop, not a cryptographic one: identityd's portion of a restore is never applied automatically — it's staged and shown to the confirming admin (profile count, roles, last activity) before they explicitly approve overwriting the live identity database, the same confirmation step §9's restore flow already requires above. A stronger, verifiable-integrity mechanism for this specific artifact is flagged as an open decision (§15) rather than assumed solved by the confirmation step alone.
- **What F10 explicitly does not cover:** The OS itself is out of scope: the appliance-image path already has its own rollback mechanism (ostree, Track E §3), and the installable-stack path's host OS is the person's own responsibility (Track E §21's stated division of labor). F10's job is exactly the data that would otherwise be lost on a hardware swap or a corrupted install — also the more valuable half of a real disaster-recovery story on hardware this replaceable and this inexpensive.

## 10. SSO / Identity Provider (F12)

Authelia in front of Track G's forthcoming G2 reverse proxy, per the master plan — both dependencies (Track G's G1, G2) don't exist yet, so this section states the design and its preconditions rather than pretending the integration can be finalized ahead of Track G's own refinement.

- **Scope at P4:** F12 fronts every browser-facing Track H service and F1's admin console (§5) with one login, replacing the per-service and F1-direct-auth bootstrapping used before it lands (§5, §7). deltos-shell and deltos-shelld are explicitly out of scope — Track C's C1 two-process model (Track C §2) is a local, non-browser-facing privilege boundary F12's browser-session model was never meant to apply to.
- **The clock dependency, confirmed:** Track E's E11 flagged session/token expiry as depending on a sane wall clock more strictly than most of that document's own scope (Track E §15). Confirmed here: F12's token validity windows assume E11's NTP sync (or its stated RTC-backed fallback) has already run before any token is issued; a box with a badly wrong clock fails closed — denies or forces re-authentication — rather than silently accepting a token whose expiry math is meaningless.

## 11. Password Vault (F13)

Vaultwarden (Bitwarden-compatible, Rust), matching the project's service-selection filter — a single-binary, self-hosted vault for managing shared credentials (a printer's admin password, a shared service account) rather than passing them around outside any system at all.

- **Admin-only at v1 — narrowed from the master plan, and a first-draft contradiction resolved:** The master plan's own F13 line names "admins and teachers" as users; the first draft of this document repeated that in prose while its own §3 permission table listed F13 access as Admin-only, an internal contradiction. Resolved in favor of Admin-only: F13 sits alongside F6 as one of the two admin-tier tools outside deltos-shell entirely (§3, §7's "teacher's surface stays in-shell" principle), and giving a teacher account un-scoped Vaultwarden access before Track G's G2/F12 login model can actually scope what that access covers (P4, §10) is itself a risk worth avoiding rather than granting by default. Whether to extend scoped vault access to teachers once F12 exists is flagged as an open decision (§15), not foreclosed permanently — just not a v1 default.

## 12. Governance (F8)

SPEC.md hosting, CONTRIBUTING docs, a public roadmap — mostly a project-process decision rather than a technical one, stated briefly here so it isn't left unaddressed entirely.

- **Where it lives:** Hosted alongside the existing public repositories (github.com/TheDataStar/wax-format and the forthcoming DeltOS repositories), not on a separate site. SPEC.md tracks the WAX format's own versioned changes, matching Track A's segment-versioning discipline; DeltOS's own architecture decisions — this eight-track set, once finalized — become the project's public roadmap artifact rather than a second document written from scratch to restate them. CONTRIBUTING itself stays a conventional, lightweight document (how to propose a pack via B9's submission pipeline, Track B §4; how to propose a spec or architecture change) rather than needing its own design work here — named for completeness, not expanded on, since nothing about it is DeltOS-specific enough to warrant more.

## 13. Documentation Site (F9)

Admin and deployment guides, per the master plan — worth one concrete decision beyond "a docs site exists."

- **Docs are also a regular content pack — dogfooding B1-B9's own pipeline:** Beyond a conventional public docs site (for anyone researching DeltOS before they have a box), the same documentation is packaged as a .wax pack through Track B's ordinary build pipeline (Track B §4) and included in the starter-pack set (Track B §7's B5 proposal). An admin troubleshooting a box that has no working internet connection yet can open the docs the same way they'd open any other installed pack, rather than needing exactly the connectivity they're trying to restore in order to read how to restore it.

## 14. Hardware & Profile Scoping

- F2, F3/F11 (identity), and F4 apply to every deployment down to Kiosk profile — a single-reader box still needs a first-boot admin account, even if never touched again, and an install pipeline, even if the person who set it up never opens F1. This means Track F's own daemons (deltos-identityd, deltos-installd, deltos-healthd — §3, §4, §6) run at Kiosk tier too, and the first draft never added them to Track E's still-open, explicitly flagged 512MB budget reckoning (Track E §5, §17) alongside rpm-ostree, Chromium, wax-serve, and Piper TTS — an omission corrected by amendment to that document (Track E §22).
- F1 (admin console) and F5 (health monitoring) matter most at Classroom profile and above, where a distinct admin or teacher role actually exists to use them — Kiosk-profile hardware may run entirely unattended after initial setup.
- F6 (fleet), F7's rotation cadence, F12, and F13 are Community Hub/Field Ops-scale concerns — a single Kiosk box has no fleet to dashboard and no shared credentials to vault.

## 18. Independent Review — Findings and Resolutions

- **[Critical]** profiles had no credential-storage column at all, and §2/§5 both referred to "the admin credential" as if it were one box-wide secret with nowhere to look it up — a genuine implementability gap given the permission table already allowed more than one admin profile. Resolved: profiles gains a password_hash column (Argon2id); each admin or teacher profile authenticates with its own credential, seeded by F2 for the first admin and set explicitly by the creating admin for any profile after that (§3).
- **[Critical]** §3's permission table listed F13 vault access as Admin-only while §11's prose described F13 as an admin-and-teacher tool, quoting the master plan directly — two parts of the same document disagreed about who gets vault access. Resolved in favor of Admin-only, aligned with §7's "teacher stays in-shell" principle, with the master plan's broader phrasing explicitly narrowed and the rationale stated rather than left as an unexplained contradiction (§11).
- **[Critical]** F4's mandatory signature-and-rollback verification was described as live from F4's own P1 landing, while Track A's own phase table scheduled that same rollback mitigation — and pack signing enforcement generally — as a P4 hardening item, "not a P0 blocker." Three documents (Track A, Track C, Track F) disagreed about when this protection actually exists. Resolved: Track A's phase table is corrected to enforce signing and the rollback check by default from P2, matching when Track B's B13 first exists to sign anything and Track C's own C6/C7 land (Track A §14); Track F's F4 is retagged to P2 to match (§4, §16).
- **[Critical]** F10's restore path wrote backed-up packs and identityd's database straight back into place with no signature check, no rollback check, and no authentication gate — a full bypass of every protection the rest of the system is built around, exploitable via nothing more than a substituted USB drive. Resolved: restored packs are re-verified through F4's normal stage-2 checks exactly as if newly installed; a fresh box always completes its own independent F2 flow before restore is even reachable; identityd's own restore requires explicit, informed admin confirmation as its stated v0.9 mitigation (§9).
- **[Critical]** F10 claimed restore worked identically on "a repaired unit or entirely different hardware" without addressing how a genuinely fresh box — which has no F1 login yet, since F2 hasn't run — could ever reach the restore action §9 gates behind F1. Resolved: restore is now explicitly sequenced after a fresh box's own F2 first-boot flow, never before it (§9).
- **[Security]** F1 is reachable from any device on the same LAN Track E's classroom AP serves to students, with no TLS, no rate-limiting, and no credential-rotation path described — a materially larger attack surface than Track C's kiosk-only IPC got, with none of the same scrutiny. Resolved: a locally-generated self-signed certificate, Secure/HttpOnly cookies, login rate-limiting, and a forced first-login password change are added as the pre-F12 baseline; a genuinely separate admin network segment is flagged as an open decision pending Track E's E3 (§5, §15).
- **[Security]** deltos-identityd is reachable by multiple callers of different trust levels (deltos-shelld, F1, C8's progress reader) with no stated authentication model — exactly the pattern Track C's own review treated as security-critical for a comparable daemon. Resolved: SO_PEERCRED-based caller allowlisting and per-caller call scoping added, mirroring Track C's C1 fix (§3).
- **[Security]** F7 described the installable-stack path's key rotation as routing through "the installable-stack path's own host-level update mechanism" — a channel Track E explicitly states is the person's own responsibility, entirely outside DeltOS's control, making the claimed distribution channel for a security-critical artifact one DeltOS doesn't actually own. Resolved: both the initial public key and its rotation are re-scoped to the installer package itself — the one artifact DeltOS does control end to end on that path (§8).
- **[Security]** Backup encryption at rest was listed only as an open decision despite the backup tree containing profile password hashes and children's progress data together, on a target as exposed as a bare USB drive. Resolved: encryption at rest is now a stated requirement, with only the specific format/library left open (§9, §15).
- **[Moderate]** F4 credited E7 with pre-seeding pack installs in a pre-boot context; Track E's actual E7 design pre-seeds only Wi-Fi credentials and Deployment Profile selection, never content. Resolved: starter packs are instead baked directly into the OS image or installer package at build time, bypassing F4 entirely for that initial state; F4's pipeline is corrected to only be exercised for installs and updates after that point (§4).
- **[Moderate]** §14 stated Track F's own daemons run at Kiosk tier but never added them to Track E's already-flagged, still-open 512MB budget reckoning, despite Track F citing that same open item elsewhere. Resolved: identityd/installd/healthd added to the enumeration, with a companion amendment to Track E (§14, Track E §22).
- **[Moderate]** Track C's C5 explicitly asked F11 for a "list profiles for this device" call; the first draft's enumeration of identityd's interface never named one. Resolved: list_profiles(device) added alongside query_role as one of the two calls deltos-shelld's callers actually need (§3).
- **[Moderate]** F1 was described as "wizard-driven," matching the master plan's own phrasing, but the section only specified deployment and authentication — no wizard or guided-flow content anywhere, a silently narrowed requirement. Resolved: F1's major consequential actions (fleet pairing, restore confirmation, profile creation) are specified as guided step sequences, with routine read-only views left as plain dashboards (§5).
- **[Moderate]** F7 stated the verification key ships "embedded in the base OS image ... both deployment paths," but the installable-stack path has no DeltOS-managed OS image to embed it in. Resolved: re-scoped per path — the OS image for the appliance path, the installer package for the installable-stack path (§8).
- **[Moderate]** Neither this document nor Track C addressed what happens when a device's 32-slot profile pool is exhausted. Resolved: exhaustion is a stated hard stop with an explicit admin-facing message, not a silent wraparound or failure; whether 32 is enough in practice is flagged as an open decision (§3, §15).
- **[Minor]** §12 named CONTRIBUTING docs in its opening sentence but never addressed them in substance. Resolved: one sentence added describing CONTRIBUTING as a conventional, lightweight document rather than requiring its own design work (§12).
- **[Minor]** §4 attributed Kiosk-tier's bandwidth/I/O queuing rationale to Track E §5's flagged budget concern, which is specifically about RAM, not bandwidth or I/O. Resolved: citation corrected to describe storage I/O as a distinct, additional concern rather than misattributing it (§4).
- **[Minor]** F2 never specified a password-hashing algorithm. Resolved: Argon2id named explicitly alongside the new password_hash column (§3).
- **[Minor]** deltos-installd's process lifecycle (persistent vs. launched on demand) was never stated, bearing directly on the Kiosk-tier memory question. Resolved: specified as a persistent, idle-when-empty daemon rather than an always-busy process (§4).

## 20. Amendment (from Track H's review)

Track H's own independent review surfaced two requirements on deltos-identityd that Track H's document — written after this one — needed but this document had not yet committed to. Both are confirmed here, on identityd's own already-scheduled P1 timeline, rather than left as one-sided assertions in Track H's document alone.

- **identityd exposes a local provisioning-event endpoint:** Track H's §2 (Identity Bridge) needs a way for third-party self-hosted services — Kolibri, Nextcloud, Conduit, Wiki.js, and the file-based adapters for DokuWiki and Grav — to learn when a profile is created, so each can provision (or, for the file-based pair, directly write) a matching account. Confirmed here: identityd (§3) adds a local HTTP endpoint, reachable only from Track G's G1 docker network (Track G §2), that emits a provisioning event on profile creation — profile_id, display_name, role, class_or_group. This is a new interface on an already-P1-scheduled component, not a new unowned deliverable, so no new phase-table line is needed; it lands wherever identityd itself lands. Authentication on this endpoint follows the same caller-scoping pattern already used for identityd's other callers (§3) — restricted to the fixed set of Track G-orchestrated adapter processes that actually need it, never open on the general docker network.
- **progress_events gains an event_source column:** Track H's §3 (Kolibri sync bridge) needs to write Kolibri lesson-completion events into the same progress_events table Track C's C8 already reads (§3), but Kolibri's own lesson IDs and WAX's archive_uuid values are two incompatible ID namespaces that pack_id alone can't distinguish. Confirmed here: progress_events gains an event_source column (wax_pack today; kolibri and any future non-pack source added as they're built), with pack_id's meaning defined relative to whatever event_source names. This is a genuine schema change to an already-settled table, made the same way Track A's entries table absorbed redirect_to and title — directly, in the schema itself (§3) — rather than left as prose describing a capability the table doesn't actually carry.

## 21. Amendment (from UX/Design-Language Research)

A competitive review of comparable offline-first and classroom platforms — done while drafting the DeltOS Visual & UX Design Language document — surfaced one real gap this document left unaddressed: nowhere does F3/F11 say how a student profile actually gets created or how a student authenticates. §3's permission table and credential-storage design cover admin and teacher profile creation explicitly; student profiles were silently assumed to work the same way, which doesn't hold up.

- **Student profiles are passwordless by design, not merely by omission:** Kolibri — the LMS this project already embeds as H1 — treats passwordless sign-in for learners as a first-class, deliberately-designed facility setting, precisely because young children can't reliably type or remember a password; ChromeOS's own classroom deployments cite exactly the opposite choice (per-student password login on shared devices) as one of their most consistently reported sources of classroom time lost to sign-in friction. Confirmed here: password_hash is nullable for student-role profiles, never for admin or teacher. A student profile is created by a teacher or admin (through F1 or C10's onboarding wizard, C5), and a student's own path to select "which profile am I" is a tap/click identification against the class roster — Track C's own switch-profile screen, specified in the Design Language document — not a password prompt. This keeps DeltOS consistent with the identity model of the LMS it already ships, rather than inventing a stricter one for its own shell.
- **F6's fleet-dashboard UI is now specified, not still open:** §7 above deliberately scoped itself to fleet discovery and trust ("that's most of this section's real content, not the dashboard UI itself"). The actual dashboard — device status vocabulary, grouping/tagging, and bulk actions across many boxes — is now specified in the DeltOS Visual & UX Design Language document, informed directly by patterns from balenaCloud's and Portainer's own fleet/container consoles. Nothing about F6's discovery/pairing design above changes; this just closes the deliberately-left-open UI question with a concrete answer.

## 22. Amendment (per product direction on Guest access)

The product owner settled the open question the Design Language document raised (its §19, and Track C's §22): every user of a DeltOS box has a real profile — there is no unenrolled, fully anonymous access path anywhere in the system — but an admin may opt in to a single, general-purpose Guest profile with deliberately narrow access, matching the familiar "guest login" pattern at a library or school computer lab. This is a fourth role, not a bypass of the role system §3 already defines.

- **One shared Guest profile per device, admin-toggled and off by default:** F1's admin console (§5) gains a single setting — "Allow Guest access" — off by default, matching the general principle that access is opt-in rather than assumed. When enabled, exactly one Guest profile exists on that device (not one per visitor); it's a normal row in the profiles table like any other, consuming one profile_slot the same way any profile does (§3) — no special-casing needed in Track C's per-(pack, profile-slot) isolation design (Track C §5, §6). Disabling the setting again removes the Guest tile from the switch-profile screen immediately; it does not need to delete the underlying profile row, since nothing writes meaningful per-guest state to it in the first place (see below).
- **Passwordless, like a student profile — for the same reason:** A walk-in library patron or community-hub visitor can't be expected to hold a credential any more than a young student can (§21 above). Guest authenticates by tap/click selection on the switch-profile screen, no password, exactly like a student-role profile — the two share the same passwordless mechanism in identityd, differing only in role and permission scope.
- **query_role and the permission model both grow a fourth value:** query_role(profile_id) (§3) now returns {admin, teacher, student, guest, none}; profiles.role's set of valid values grows to match. The table below supersedes §3's three-column version for implementation purposes — every row from that table still holds for Admin/Teacher/Student exactly as written; Guest is added as the new, most-restricted column:

| **Operation** | **Admin** | **Teacher** | **Student** | **Guest** |
|---|---|---|---|---|
| install_pack / remove_pack (Track C C1) | Yes | No | No | No |
| mount_removable (Track C C1) | Yes | No | No | No |
| join_network / configure_ap (Track E E3) | Yes | No | No | No |
| create/manage profiles in own class (F3/F11) | Yes | Yes | No | No |
| view progress across own class (Track C C8) | Yes | Yes | No | No |
| view own progress only (Track C C8) | Yes | Yes | Yes | No |
| browse/launch content packs (Track C C2) | Yes | Yes | Yes | Restricted — see below |
| F1 admin console access (§5) | Yes | No | No | No |
| F6 fleet pairing / F13 vault access (§7, §11) | Yes | No | No | No |

- **"Limited access to certain tools and features," made concrete:** Guest's content-browsing scope (C2, Track C §3) is a manifest-declared subset, not the full catalog: B3's manifest schema (Track B §2) gains an optional guest_accessible boolean, defaulting false, that a pack's own author or the admin sets explicitly. A pack with no opinion set is hidden from Guest's launcher grid entirely — the same "conditionally present, not shown-then-blocked" principle Track C's C11 already uses for hardware-tier absence (Track C §11) — rather than shown and then refused. This keeps the restriction legible (a guest sees a smaller, deliberately curated grid, not an error) and keeps the default safe (a new pack is invisible to Guest until someone opts it in, not visible until someone remembers to opt it out).
- **No identity-bridge provisioning for Guest, by default:** Track H's Identity Bridge (Track H §2) provisions a DeltOS profile into third-party self-hosted services (Kolibri, Nextcloud, Conduit, Wiki.js) on profile creation. Guest is excluded from this by default, for a different reason than Gitea's exclusion (Track H §2): those services model persistent per-user state (files, messages, course progress) that a shared, anonymous identity has no meaningful claim to, and provisioning one "Guest" account that every walk-in visitor shares would create exactly the kind of ambiguous, unaccountable shared credential this project's own F13/F3 design has otherwise avoided. Confirmed in a companion note to Track H (Track H §18).
- **No progress tracking, no personal storage:** Because Guest is a single shared identity rather than a per-person one, C8's coach dashboard (Track C §8) and any per-profile storage quota (H5, Track H §5) simply don't apply to it — there is no "Guest's progress" or "Guest's files" to track in a way that would be meaningful, and this document does not invent one. A visitor who wants their own tracked progress needs their own profile, created by a teacher or admin the ordinary way (§21).

## 23. Amendment (per product direction — catalogue additions)

Each states its **goal**, the **property that must hold**, and **why**. All are subject to the app contract (cross-track contract §15) and measured-resource gating (§2).

### 23.1 Usage Insights (F14)

**Goal.** Show which packs actually get used.

**Property.** **Aggregate only, never per learner, and it never leaves the box.** Contract §16 states that DeltOS has no telemetry at all; **F14 is the single named exception to that rule**, and it is an exception only in the sense that the data is collected — not in the sense that anything is transmitted. Nothing is reported outward.

**Why.** A librarian choosing what to put on a box with finite storage is guessing without this. It is named as the sole exception in the contract precisely so that "we already collect usage data" can never be used to justify a second collector later.

### 23.2 Network Defense (F15)

**Goal.** The box protects itself.

**Property.** Intrusion detection on its own Wi-Fi, scheduled self-scans of its own services, blocking of repeated failed logins, and alerts in the admin view. **Its scope is the box.** It scans the box's own services and watches the box's own network — it is not a tool pointed outward, and it shares no machinery with H19's security lab, whose targets are authorised separately.

**Why.** A box in a school runs a dozen services on an open network with no administrator watching it most of the time. Failed-login blocking alone closes the most common real attack against such a deployment. Keeping F15's scope explicitly self-directed is what keeps it distinct from H19 — one defends this box, the other teaches.

### 23.3 Visible Benchmark (F1)

**Goal.** Surface the box's own measured capability in the admin console: what this box can run, and why.

**Property.** It reads the **capability record** (contract §9) and the declared floors of installed apps (§15), and shows the comparison that gating actually performs. **It reports measurements, never a device name** — there is no longer a tier to display.

**Why.** With capability now following measured resources, "why can't this box run the larger model?" has a real answer, and an administrator should be able to see it rather than infer it. This is also the honest consequence of retiring tier names: the name used to be the explanation, so something has to take its place.

### 23.4 Remote Bridge (Track F)

**Goal.** Remote administration when internet is present.

**Property.** **Opt-in, admin-only, and off by default.** All three, independently.

**Why.** Fleets of boxes in reachable locations are genuinely easier to support with a bridge, and a box that can be administered remotely without the owner's deliberate action is a box the owner does not control. Off by default is the part that matters.

### 23.5 F10 backup/restore covers the new surfaces

**Goal.** Backups cover everything people create, not only content and progress.

**Property.** F10's set now includes **hosted sites (H18), security-lab work (H19) and code-studio projects (H12)** alongside content and progress data. F10 learns about them through the **durability group of each app's manifest** (contract §15.1), not through per-service knowledge coded into F10.

**Why.** Every one of the new components lets someone create something durable, and a backup that silently omits a learner's own work is worse than no backup — it is a promise that fails exactly when it is needed. Sourcing the set from manifests is what stops the omission recurring with the next addition.
