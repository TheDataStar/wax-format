# DeltOS — Track C

DeltOS Shell — Technical Refinement

*Working draft · September 2026 · third of eight per-track refinements, revised after independent technical review (§16) and seven rounds of cross-track amendment (§17-§23)*

## 1. Scope

Track C owns the surface a student, teacher, or community member actually touches: the kiosk launcher, the search bar, per-pack isolation, profiles, the app store, accessibility, onboarding, and the conversational assistant. It sits on top of Track A (reads packs via A5/A9), Track B (reads manifests via B3/B4), Track D (search/RAG), and Track F (identity, install pipeline, first-boot) — this document treats all four as settled and specifies exactly what Track C expects from each, flagging where an assumption needs the owning track to confirm it.

## 2. Shell Architecture (C1)

"Privileged PWA over Chromium/WebKit" undersells the one decision that has to be made correctly in P0: a kiosk browser tab has no legitimate way to install a pack, mount a USB drive, or write to the on-device catalog (B4) — those need real filesystem and process privileges a web page must never hold directly.

- **Two-process model:** The shell is two things, not one: deltos-shell, an unprivileged web app (the launcher UI, search bar, settings) rendered full-screen in Chromium/WebKit kiosk mode; and deltos-shelld, a small native helper (Rust, matching Track A's language choice) running with the actual privileges — mounting USB media, invoking F4's install pipeline, writing to B4, launching per-pack wax-serve instances. The two talk over a local Unix-socket IPC API that deltos-shell reaches through a narrow, purpose-built bridge — never a general "run this shell command" call.
- **Why this split matters:** Every pack a device installs is third-party content by definition (B9's review notwithstanding — review reduces risk, it doesn't eliminate it). If the shell UI and the privileged operations shared one process and origin, a single content-pack sandbox escape (C4) would inherit install/filesystem privileges for free. Splitting them means a sandbox escape is contained to what deltos-shelld's narrow IPC surface exposes, not the whole box.
- **Recommendation:** Ship deltos-shelld's IPC surface as a fixed, versioned set of operations (install_pack, remove_pack, mount_removable, launch_pack_server, get_catalog) rather than anything resembling a generic RPC — the smaller and more specific that surface is, the easier A4-style conformance testing and later security review become.
- **Caller authentication (added after review):** The two-process split only holds if deltos-shelld can tell deltos-shell's own top-level page apart from a pack running on an adjacent 127.0.0.1 origin (C4) — otherwise a malicious pack simply speaks the same protocol directly. If the bridge is a genuine Unix domain socket reachable only from local processes (not from browser JS), OS-level peer-credential checking (SO_PEERCRED) is enough. If any part of the bridge is exposed as a localhost WebSocket/HTTP endpoint reachable from browser-hosted content — a real possibility, since a stock Chromium kiosk build has no Electron-style preload bridge — deltos-shelld must also check the WebSocket handshake's Origin header against an allowlist of exactly deltos-shell's own origin, plus a per-session capability token issued to deltos-shell at shell startup and never exposed to a pack's origin, as defense in depth beyond Origin checking alone.
- **Role-gated operations (added after review):** Every privileged operation deltos-shelld exposes (install_pack, remove_pack, mount_removable) must check the active profile's role — sourced from Track F's F3 — before executing, not just verify the caller is deltos-shell. Without this, a student profile (C5) on a shared classroom kiosk could install or remove content or mount arbitrary USB media through the same UI a teacher uses. Flagged as a stated dependency on F3's role model, the same way §8 flags C8's dependency on F11.

## 3. Pack / App Registry (C2)

The launcher grid's data source was left ambiguous in the master plan — "reads manifests (B3)" could mean opening every installed .wax file's index directly, or reading B4's already-denormalized cache. It has to be the latter.

- **Recommendation:** For actual WAX content packs, C2 reads exclusively from B4's on-device catalog (Track B §5), never from a pack's own index directly. B4 already carries manifest_json per pack precisely so nothing downstream needs to open a .wax file just to draw a launcher tile — opening the archive is reserved for the moment a pack is actually launched (handed to C4).
- **C2 is multi-sourced, not B4-only (corrected after review):** B4 is the source for WAX content packs, but it isn't the registry's only source: C11 (Ask DeltOS, §11) is shell-native and never has a B4 catalog row, and Track H's services (LMS, media server, office suite, etc.) are Track G-orchestrated containers rather than .wax archives with B3 manifests, so they can't acquire a B4 entry either as currently specified. C2's grid is therefore populated from B4 (content packs) plus a small static/shell-native registry entry for C11, with how Track G/H-launched services register a launcher tile left as an explicit open item for those tracks' own refinement passes (§13) rather than asserted here.
- **Change notification:** C2 needs to know when B4 changes (an install completes, a catalog-index sync lands new metadata, §5 of Track B) without polling a SQLite file on a timer. Recommendation: B4's writer (F4's install pipeline, or the catalog-index sync job) emits a local event (a Unix-socket pub/sub message via deltos-shelld, §2) on any change; C2 subscribes and re-renders. Polling stays as the fallback for the rare case a notification is missed, not the primary mechanism.
- **Grid grouping:** Grouped by B3's category field, consistent with Track B's revised scope for that field (Track B §2 — category drives launcher grouping only, not Profile gating).
- **Deployment Profile filtering — scoped out for v1 (added after review):** The master plan implies Profiles gate what a box is offered, but Track B's settled B13 design (Track B §5) distributes one flat catalog-index to every box, with no per-profile variant. Rather than reopening Track B's already-reviewed schema for this, v1 treats Profile-based catalog curation as out of scope: every box sees the full catalog, and B3's min_hw_tier (Track B §2) is the only automatic filter C2 applies. Profile is a human-facing label for which starter packs a wizard suggests (C10, §10), not an enforcement mechanism C2 implements. Revisiting this is a candidate for a later Track B amendment, not a Track C decision to make unilaterally.

## 4. Unified Search Bar (C3)

The master plan says C3 "queries every installed pack via Track D's API" without saying whether that's one call or many. This is Track D's contract to own, but Track C has to state what it assumes so D's own refinement pass can confirm or correct it.

- **Assumed contract:** A single local endpoint that already does cross-pack aggregation and ranking — C3 sends one query and renders one ranked result list. C3 explicitly does not fan out to each pack's own A9 search-index section and merge results itself; that logic already has to exist for D8's federated (cross-box) search, and building it twice (once in C3, once in D) would let the two drift out of sync exactly the way B4/B13 did before Track B's review caught it.
- **Degraded mode:** On hardware where D7's tier gating disables ranked/semantic search (D1's Tantivy tier, D2's vector index), C3 still needs a result to show — falling back to whatever tier IS available (v0.9's FTS5 form, per Track A §7) rather than the search bar simply not working on lower-tier hardware.
- **Open decision:** Whether that single endpoint is a REST call, a local WebSocket (for incremental/streaming results, useful once C11's RAG answers stream tokens), or both. Flagged for Track D's own refinement to settle — noted here so it isn't independently decided twice.

## 5. Per-Pack Sandbox & Origin Isolation (C4)

"iframe+CSP now, WASM later" is a real security boundary, and it has a gap the master plan's one-line description doesn't surface: an iframe alone does not give two packs separate storage. Two packs loaded from the same origin share localStorage, IndexedDB, and cookies unless something explicitly separates them.

- **Per-(pack, profile-slot) origin — revised after review:** Each installed pack is served by its own A5 wax-serve instance (launched by deltos-shelld, §2) bound to a distinct local origin. The first draft keyed that origin by pack alone (127.0.0.1:41000+N); review caught that this does not isolate profiles (§6) at all, since a browser's storage bucket is fixed by origin and telling the server which profile is "active" doesn't change it. Corrected scheme: the port is derived from (pack_index, profile_slot), where profile_slot is a small, bounded number (e.g. 0–31) assigned to a profile record at creation time by C5/F11 and stable for that profile's life — not the profile's full identity, just a slot index. A box's baseline (single-reader Kiosk) case is simply slot 0. This makes a profile switch a genuinely distinct origin per pack, not a relabeled request to the same one, and it bounds the port range to (pack count × slot count) rather than growing unboundedly.
- **Cookies are not isolated by this scheme — addressed after review:** Distinct ports on the same host (127.0.0.1) give real isolation for localStorage, IndexedDB, and the Cache API, which are scoped by full origin (scheme+host+port). They do not isolate cookies: per RFC 6265, a cookie's scope ignores port, so a cookie set by any pack would be sent to and readable from every other pack's and profile's origin on the box. Fix: wax-serve never emits Set-Cookie for pack content and strips any Cookie header before it reaches a pack's own code — packs needing client-side persistence use IndexedDB/localStorage (correctly port-scoped) instead, not cookies.
- **Slot reuse must wipe storage — addressed after review:** When a profile is deleted and its slot is later reused by a new profile, or when a pack is uninstalled and reinstalled into the same port, the previous occupant's storage at that origin must be explicitly cleared (a CDP "Clear browsing data for origin" call via deltos-shelld) before the origin is handed to its next occupant — otherwise a reused slot or port silently exposes the prior student's or prior pack version's residual data.
- **iframe sandbox attributes:** Loaded with sandbox="allow-scripts allow-same-origin" and no more — no allow-top-navigation, no allow-popups, no allow-forms unless a pack's manifest explicitly declares it needs one (a new, narrow manifest capability flag, flagged as an open decision below rather than designed in full here).
- **Shell↔pack bridge:** A pack talks to the shell (e.g. to report progress for C8) only through postMessage, against a fixed, versioned message schema deltos-shell validates before acting on — the same "narrow surface, not a generic channel" principle as C1's IPC design.
- **WASM isolation (later phase):** The Wasmtime path in the master plan is for packs that need to run actual code beyond static HTML/JS-in-iframe (e.g. a compiled app). Deferred — it doesn't change the origin-isolation design above, which holds either way.

## 6. Multi-Profile / Classroom Mode (C5)

Layering profiles on top of C4's per-pack isolation makes this a two-dimensional partitioning problem, not a one-dimensional one — a naive implementation would isolate packs from each other but let every profile on a shared kiosk see the previous student's session inside the same pack.

- **Partition key — corrected after review:** Every profile is assigned a bounded profile_slot at creation, and every pack origin is keyed by (pack, profile_slot) as specified in §5's revised scheme — not by simply telling wax-serve which profile is "active" against a fixed origin, which the first draft proposed and which review showed does nothing (a browser's storage bucket is fixed by origin, not by a label passed to the server). Switching profiles changes which origin — and therefore which storage partition — a relaunched pack is served from.
- **Profile switch, not OS user switch:** Profiles are an application-level concept inside one OS session — not separate Linux user accounts and not a full browser-profile switch (too slow for a classroom changeover between periods). This keeps profile switching fast, at the cost of relying on C4's partitioning being correct rather than the OS's own user-isolation guarantees — an explicit tradeoff, not an oversight.
- **Data model dependency:** The actual profile records (who exists, which class they're in) are F11's responsibility (Track F, still an open cross-track question per the master plan §5). C5 only needs F11 to expose a stable profile_id and a "list profiles for this device" call — the rest of F11's shape doesn't block C5's design.

## 7. Offline App Store & Install Flow (C6, C7)

The master plan describes these as two features; they should be one code path with two entry points, or install logic and USB/peer install logic will quietly diverge.

- **One pipeline, two sources:** C6 (browsing B4's catalog) and C7 (USB/peer install) both terminate in the same call to F4's install/update pipeline (Track F) — the only difference is where the .wax bytes and manifest come from (a catalog-index-driven download, Track B §5, vs. a locally-mounted USB path or a peer box's address). C6's UI shows install progress by reading F4's queue state, not by tracking progress itself.
- **USB/peer trust:** A pack arriving via C7 hasn't necessarily passed B9's review pipeline the way a catalog pack has. F4 needs to apply the same signature check (Track A A7, verified against B13's project key) regardless of source — C7 is a different delivery mechanism, not a different trust policy. An unsigned or unrecognized-signer pack from USB/peer should be installable only behind an explicit "install from unverified source" admin-level confirmation, not silently treated the same as a catalog pack.
- **Rollback check applies here too (added after review):** C7 is precisely the delivery path Track A §6's rollback mitigation was written for: a validly-signed but stale pack has no network freshness check to fail when it arrives over USB or peer sync. F4 must apply Track A's "highest archive_uuid+version seen" tracking to every install regardless of source, not only to catalog-sourced updates — otherwise a stale, still-validly-signed pack reintroduced via C7 sails through the checks above unnoticed.
- **Dynamic requirement calculator — added per product direction (Track E §21):** C6's browse view gains a persistent selection tray: as the person checks packs/tools to install (or unchecks ones already installed), a live readout recomputes minimum and optimum system requirements for the current selection, summing each pack's B3 runtime_ram_bytes/runtime_storage_bytes (Track B §17) against Track E's E6 tier table (Track E §5). This replaces any notion of a single fixed "optimum spec" — the readout is specific to what's actually checked, updates as the selection changes, and never blocks a selection outright even if it would exceed the box's own detected tier; it labels the shortfall and lets the person or admin decide (skip it, install anyway and accept degraded performance, or note it for a hardware upgrade). The same calculation is exposed as a plain read function so the download-time website configurator (an open decision, Track E §17, not yet owned by any track) can call it against the same per-pack data without duplicating the arithmetic.

## 8. Coach / Progress Dashboard (C8)

C8 is explicitly blocked on F11 (identity & progress data model) per the master plan's own open question — this section states what C8 needs from F11 so that track's refinement has a concrete target rather than a blank page.

- **Assumed event shape:** A progress event needs at minimum: profile_id, pack_id, event_type (e.g. opened, completed_unit, score), a timestamp, and a small free-form payload for pack-specific detail (a quiz score, a page reached). Packs emit these through C4's postMessage bridge; C8 reads them back out of wherever F11 decides to store them — C8 doesn't need to own storage, only the read side and the dashboard rendering.
- **Non-blocking scope:** Everything else about C8 (what the dashboard actually displays, per-class rollups, exportability) can wait for F11 to land without blocking Track C's other components — C8 is the one component in this document genuinely gated on another track's decision, and it's called out as such rather than designed around an assumption that might not hold.
- **Timing risk, stated plainly (added after review):** The master plan only commits to deciding F11's owner by P2 — not to F11's schema being finished by then. §14 provisionally slots C8 into P3 on that basis, but that slot is contingent on Track F's own refinement actually delivering a workable F11 design in time; if it slips, C8 slips with it. This isn't treated as a hidden risk — if Track F's refinement lands F11 later than P2, C8's phase tag in §14 needs revisiting rather than being quietly missed.

## 9. Accessibility Layer (C9)

TTS, translation, and high-contrast/large-text turn out to need three different technical answers, and one of them runs directly into C4's isolation design.

- **Text-to-speech, tier-gated (revised after review):** Recommend Piper (a small, fast, fully offline neural TTS engine) bundled with the shell, rather than the browser's built-in Web Speech API — Web Speech's local-voice quality and availability varies by device/OS in a way that's inconsistent with shipping a fixed appliance experience. Piper's smallest voice models are genuinely lightweight, but the first draft asserted this as a flat feature down to Kiosk tier (Pi Zero 2W, 512MB RAM) — hardware already running Chromium kiosk mode plus one or more per-pack wax-serve instances (§5) — without checking the budget. Corrected: Piper ships on every tier as a baseline accessibility feature (not gated behind D7 the way translation is, since accessibility shouldn't be the first thing a constrained box drops), but its footprint against real Kiosk-tier headroom needs validating before that commitment is final — see the open decision below.
- **Translation:** Tiered per D7's hardware-gating model rather than a flat feature: on Kiosk-tier hardware, translation is likely out of scope entirely (no spare capacity for a model of any size); on Community Hub-tier and above, this is a good candidate to reuse D5's local LLM runtime rather than bundling a second, separate translation model — one model doing double duty, gated the same way D7 already gates everything else.
- **High-contrast / large-text — the real gap:** This is a shell-level (deltos-shell) presentation layer for its own UI, which is straightforward. But it cannot reach inside a pack's sandboxed iframe (C4) to restyle that pack's own content — the same origin isolation that protects packs from each other also blocks the shell from injecting an accessibility stylesheet into them. Recommendation: don't try to fight the sandbox. Ship a shell-level "reader mode" that, where a pack's content is plain HTML (most reference/text packs), extracts and re-renders it in a shell-controlled view instead of restyling the iframe in place. This explicitly does not cover every pack type (a canvas-rendered app, for instance, has no extractable HTML to re-render) — a stated v1 limitation, not a silent gap.
- **Reader mode's extraction mechanism, made concrete (added after review):** The first draft didn't say how the shell actually gets a cross-origin pack's HTML out of its iframe — and under C4's real cross-origin isolation (§5), the parent frame's JS cannot simply read a cross-origin iframe's DOM; sandbox attributes don't change that. Loosening wax-serve's CORS policy for the shell's origin would quietly reopen the isolation §5 just closed, so that's ruled out. Instead, reader-mode support is opt-in per pack: a manifest capability flag (the same new flag §5 already needs for allow-forms, open decision below) declares a pack supports reader mode, and such a pack's own script exports its content via the existing postMessage bridge (§5) in response to a shell request — a narrow, pack-authored export, not a shell-side DOM read. Packs that don't declare the flag simply don't support reader mode, which is a stricter but honest version of the original "not every pack type" limitation.

## 10. First-Boot Onboarding Wizard (C10)

The master plan lists this once but it's actually two tracks' work, the same kind of overload B4/wax-hub had before Track B's review split it — worth fixing here before it causes the same confusion.

- **Split:** F2 (Track F) owns the security-critical first-boot step: forcing a unique generated admin password before the box does anything else. C10 (this component) owns everything after that: the DeltOS Shell-side wizard UI — network setup, Deployment Profile selection, initial starter-pack selection (Track B §7's B5 bundles), and first-profile creation (C5) — wrapping F2's step as its first screen rather than duplicating it.
- **No raw config exposure:** Every choice the wizard makes (Wi-Fi credentials, which starter packs to install) is written through the same privileged paths the rest of the shell uses — deltos-shelld's IPC (§2) and F4's install pipeline (§7) — never a raw config file the wizard edits directly, which is what the master plan's "no raw config files exposed" line is protecting against.

## 11. Ask DeltOS (C11)

Built into the shell as a first-class app rather than a bolt-on — that phrasing needs one clarification: does "first-class" mean it's exempt from C4's per-pack sandbox, or is it just another sandboxed pack with a nicer name? It has to be the former.

- **Shell-native, not sandboxed:** C11 is deltos-shell code, not a downloaded content pack — it never goes through B4's install path or C4's per-origin isolation, because it isn't third-party content. It calls Track D's D5/D6 RAG endpoints directly over the shell's own privileged local IPC, the same category of call C1's helper process already exposes.
- **Network scoping, defense in depth:** Even as shell-native code, C11's CSP is restricted to localhost-only origins (D5/D6's local endpoints) — being exempt from the pack sandbox is not the same as being trusted to reach the open internet, which this appliance category shouldn't be doing regardless.
- **Hardware-tier absence, not failure:** On hardware where D7 gates out D5 (the local LLM runtime) entirely — Kiosk tier most likely — Ask DeltOS should not appear in the launcher grid at all, rather than appearing and failing when tapped. C2's registry rendering (§3) needs to treat C11 as conditionally present based on D7's tier signal, the same way any other hardware-gated feature would be.
- **Untrusted retrieved content, answer-only in v1 (added after review):** C11 is the single most privileged surface reachable by pack-originated text: it holds shell-level IPC access, yet D6's RAG pipeline retrieves passages from installed packs — including, per C7, packs that haven't necessarily passed B9's review. That combination is a real indirect-prompt-injection surface if left unaddressed. Two firm rules, not left implicit: retrieved passages are always treated as untrusted data in the prompt, never as instructions to follow; and in v1, C11 is answer-only — it never has function-calling access to deltos-shelld's IPC surface (§2) at all, regardless of what a model response contains. Any future version that lets Ask DeltOS take actions (install a pack it recommends, say) needs its own explicit confirmation-gated design, not a quiet extension of this one.

## 12. Hardware & Profile Scoping

- C1's two-process split, C2's registry, and C4's sandbox model apply on every tier down to Kiosk (Pi Zero 2W) — this is the baseline shell, not an add-on.
- C5 (multi-profile) and C8 (coach dashboard) are meaningful primarily at Classroom tier and above; a single-reader Kiosk deployment can run with exactly one implicit profile and simply not surface the switcher UI.
- C9's translation tier and C11's presence are both gated by D7's hardware signal, not by Deployment Profile directly — two boxes on the same Profile but different hardware tiers can legitimately show a different feature set.

## 13. Open Decisions Needed Before Implementation

- Settle C3's search-endpoint transport (REST vs. WebSocket, §4) once Track D's own refinement pass addresses D1/D6 — noted here so it's asked once, not decided independently by both tracks.
- Define the manifest capability-flag mechanism referenced in §5 and §9 (a pack declaring it needs allow-forms, another relaxed sandbox permission, or reader-mode export support) — this needs a small amendment to Track B's B3 manifest schema, parallel to how redirect_to and title were amended into Track A during Track B's design and review.
- Confirm with Track F whether F11's progress-event storage can accept the shape assumed in §8, or whether C8's assumption needs revising once F11 is actually designed — and revisit §14's P3 tag for C8 if F11 slips past P2 (§8).
- Confirm with Track F what F3's role model exposes and how deltos-shelld queries it (§2) — C1's role-gating on privileged IPC operations assumes a queryable role per active profile, which Track F's own refinement needs to confirm it can provide.
- Decide whether per-pack, per-profile-slot local origins (§5) are ports on 127.0.0.1 or distinct hostnames/subdomains behind G2's reverse proxy (Track G) once G2 is further along. Note from review: this is a choice between two isolation-preserving schemes only — a path-based scheme under one shared hostname was considered and ruled out, since same-origin policy is defined by scheme+host+port and ignores path entirely; routing packs to different paths on one host:port would silently destroy the isolation §5 relies on, not just relocate it.
- Validate Piper TTS's actual memory/CPU footprint against real Kiosk-tier (Pi Zero 2W) headroom, alongside Chromium kiosk mode and per-pack wax-serve instances, before treating §9's tier-independent commitment as final.

## 15. What This Unblocks

- Every other track gets a real surface to demo and test against once C1/C2/C4 exist in P0/P1 — nothing in Tracks A, B, or D can be shown to an actual user before this.
- Track F's F4 (install pipeline) and F11 (identity/progress model) both get a concrete consumer (§7, §8) to design against instead of an abstract UI requirement.
- Track B's B3 manifest schema gets one more forward-looking amendment flagged (§13's capability flag) before implementation, continuing the pattern of catching schema gaps during design rather than after.

## 16. Independent Review — Findings and Resolutions

- **[Critical]** C5's profile-partitioning scheme couldn't actually isolate anything — labeling a request to a fixed origin as "this profile is active" doesn't change the browser storage bucket that origin maps to. Resolved: origins are now keyed by (pack, profile_slot), a bounded per-profile index, so a profile switch is a genuinely distinct origin per pack (§5, §6).
- **[Critical]** The path-based-origin alternative floated in the original open decisions would have silently destroyed C4's isolation if ever chosen — same-origin policy ignores path entirely, so two packs behind different paths on one host:port are the same origin. Resolved: struck from the option set; only distinct hostnames/subdomains remain as the G2-compatible alternative to per-pack ports (§13).
- **[Critical]** Cookies are scoped by host only (RFC 6265), not by port — so the original per-pack-port scheme left every pack's and profile's cookies readable across every other origin on the box, undermining both C4 and C5. Resolved: wax-serve never emits or forwards cookies for pack content; packs use IndexedDB/localStorage instead, which are correctly port-scoped (§5).
- **[Critical]** C2 asserted it reads "exclusively" from B4, but C11 (shell-native, no B4 entry) and Track H's Track-G-orchestrated services (not .wax archives with B3 manifests) both need launcher tiles with no way to get one under that rule. Resolved: C2 is now explicitly multi-sourced, with Track G/H's own registration mechanism left as an open item for those tracks rather than asserted here (§3).
- **[Security]** deltos-shelld's IPC bridge had no stated caller authentication — if any part of it is reachable as a localhost WebSocket/HTTP endpoint (plausible without an Electron-style preload bridge), a malicious pack on an adjacent origin could speak the same protocol directly, defeating the entire rationale for C1's two-process split. Resolved: added Origin-header allowlisting and a per-session capability token as defense in depth, alongside OS-level peer-credential checking where the transport is a genuine Unix socket (§2).
- **[Security]** No privileged IPC operation (install_pack, remove_pack, mount_removable) checked the active profile's role, so a student profile on a shared kiosk appeared able to install or remove content. Resolved: role-gating added, sourced from Track F's F3, flagged as a stated dependency the same way C8 depends on F11 (§2).
- **[Security]** The reader-mode accessibility workaround assumed the shell could extract a cross-origin pack's HTML for re-rendering, which C4's own isolation model doesn't actually permit — and loosening CORS to allow it would reopen the isolation gap §5 exists to close. Resolved: reader mode is now opt-in per pack via a manifest capability flag, with the pack's own script exporting its content through the existing postMessage bridge rather than the shell reading across the origin boundary (§9).
- **[Security]** C11 combines shell-level privilege with RAG-retrieved content from packs that may not have passed review — an unaddressed indirect-prompt-injection surface, since C11 is the most privileged thing pack-originated text could reach. Resolved: retrieved passages are now explicitly treated as untrusted data, and C11 is scoped to answer-only in v1 — no function-calling access to deltos-shelld's IPC regardless of model output (§11).
- **[Security]** C7's USB/peer trust discussion covered signature validity but never invoked Track A's rollback mitigation, despite USB/peer delivery being exactly the no-freshness-check scenario that mitigation targets. Resolved: F4 now applies Track A §6's "highest version seen" tracking to every install regardless of source (§7).
- **[Moderate]** Port/slot reuse (an uninstalled-then-reinstalled pack, or a deleted profile's slot reassigned to a new profile) had no stated storage-clearing step, risking a new occupant inheriting a prior occupant's residual data at the same origin. Resolved: explicit storage-clear on reuse, folded into the same fix as the profile-slot redesign (§5).
- **[Moderate]** Piper TTS was assumed to run everywhere down to Kiosk tier without checking its footprint against hardware already running Chromium kiosk mode plus per-pack wax-serve instances. Resolved: kept as a tier-independent baseline commitment (accessibility shouldn't be the first thing dropped on constrained hardware) but flagged for footprint validation before that commitment is treated as final (§9, §13).

## 22. Amendment (from UX/Design-Language Research)

A competitive review of comparable offline-first and classroom platforms — done while drafting the DeltOS Visual & UX Design Language document — surfaced two real gaps in this document's coverage and one open product-scope question worth recording rather than deciding unilaterally.

- **C10's wizard is missing a language/accessibility step:** §10 lists the wizard's screens as F2's admin-password step, network setup, Deployment Profile selection, starter-pack selection, and first-profile creation — nowhere does language or an accessibility preference get asked. ChromeOS's own first-boot flow asks language, keyboard layout, and accessibility options before anything else, including before network setup; ours has no equivalent step despite §9 defining real accessibility features (Piper TTS, translation, high-contrast reader mode) a user would want active from their very first screen, not discovered later in a settings menu they may never open. Resolved: C10 gains a language-and-accessibility screen as its second step, immediately after F2's admin-password screen and before network setup — asked early enough to apply to the wizard's own remaining screens, not just to the shell once onboarding finishes.
- **C9 has no screen-magnification feature:** §9 covers TTS, translation, and high-contrast/large-text thoroughly, but nothing addresses low-vision magnification — a cheap, well-precedented accessibility feature (a docked or full-screen magnifier is standard on ChromeOS and other major platforms) that costs little relative to what §9 already ships. Resolved: a shell-level magnifier (a docked mode over a region of the screen, plus a full-screen mode) is added to C9's scope, implemented as deltos-shell presentation-layer zoom rather than anything reaching into a pack's sandboxed iframe — the same C4 boundary §9 already respects for high-contrast/reader mode.
- **Passwordless student profiles need a shell-side switch-profile screen:** Track F's own companion amendment (Track F §21) makes student profiles passwordless, matching the identity model Kolibri (H1) already uses for the same reason. That needs a concrete shell-side counterpart: C5's profile switcher is a tap/click roster of that device's profiles (avatar or name tile per profile, sourced from identityd's list_profiles call, Track F §3) rather than a password-entry form, with a password prompt shown only when the selected profile is admin or teacher. Specified concretely in the Design Language document; no change to C5's existing storage-isolation design (§5, §6) is required.
- Open, not resolved here: whether Community Hub/Field Ops deployments should support a walk-in, unenrolled visitor (a library patron who isn't a registered profile) using non-identity-gated services without going through C5's profile system at all. §12 already covers the Kiosk-tier case (a single implicit profile, no switcher shown) — this is a different, Community-Hub-scale question about public-access scope that the product owner should settle deliberately rather than have this document assume an answer either way.

## 23. Amendment (per product direction on Guest access)

The product owner settled §22's open item: every user gets a real profile — DeltOS has no fully anonymous access path — but an admin may opt in to a single shared Guest profile with narrow, curated access, resolving the walk-in-visitor question without reopening C5's storage-isolation design. The full role/permission model lives in Track F §22; this section covers the shell-side surface only.

- **Guest tile on the switch-profile screen, conditionally present:** When F1's admin has enabled Guest access (Track F §22), C5's switch-profile screen shows exactly one additional tile alongside the device's named profiles — labeled "Guest," passwordless, tap/click to enter, identical in mechanics to a student tile (§9 of the Design Language document). When Guest access is disabled (the default), the tile simply isn't rendered — the same conditionally-present-not-shown-then-blocked principle §11 already uses for C11's hardware-tier absence.
- **C2's registry filters to guest_accessible packs only:** Track B's manifest schema gains a guest_accessible boolean for exactly this (Track B §2, confirmed there per Track F §22). C2 (§3) checks this flag only when the active profile's role is guest — every other role continues to see the full catalog per §3's existing category/min_hw_tier filtering, unaffected. A pack with no opinion set is invisible to Guest, not visible-then-refused, keeping the restriction legible as a smaller grid rather than an error state.
- **No dashboard, no dock item, nothing to switch back to that persists:** Because Guest is a single shared identity (Track F §22), C8's coach dashboard (§8) never shows a "Guest" row, and nothing about a Guest session survives Lock/session-end (§7 of the Design Language document) — the next person to tap Guest starts from the same clean state, by design, not by an unfinished feature.
