# End-to-end check of the WAX chain (2026-11-21)

**Question:** does the whole chain work together on `main`, with real inputs,
not just per-crate tests? Convert with the Wax Service Shell (`wss`), serve
with `deltd`, read in the Delt desktop window. Run on Linux x86_64 (dev
container). **Not** run on a Pi (on hold by Commander's decision).

**Answer: yes, after four fixes in this PR.** Every real input converts, every
pack serves, every link inside every pack resolves (except links that are
already broken in the source), search finds English, Belarusian, Arabic and
Japanese text across all packs at once, updates and rollbacks are picked up
live, and the desktop window lists, searches and renders them, including
Japanese vertical text with ruby.

## Defects found and fixed in this PR

1. **Japanese EPUBs lost their chapters and search.** Many real books are
   zipped without the zip "UTF-8 names" flag; the zip rule then reads names
   as CP437, so `一.xhtml` became `Σ╕Ç.xhtml`, missed the reading order, and
   the book had **no search index at all** (草枕: `search: none`). OCF requires
   UTF-8 names, so `wss` now reads a name as UTF-8 whenever it is valid UTF-8.
2. **Japanese PDFs had no text.** `pdf-extract` 0.7 asserts on any CJK font
   encoding other than `Identity-H` (e.g. `UniJIS-UCS2-H`); the panic was
   caught, so the PDF was carried but unsearchable. Upgraded to
   `pdf-extract` 0.10 (and `lopdf` 0.38 to match): both Japanese PDFs now
   extract and search.
3. **Japanese phrases did not match across ruby or inline tags.** The search
   text put a space at every tag (`<ruby>角</ruby>が` → `角 が`) and kept the
   ruby reading (`智<rt>ち</rt>に` → `智ちに`). Japanese has no spaces, so
   `wax-bigram-16` lost the pairs across the break and the novel's first
   line, 智に働けば角が立つ, was not found. `wax-core`'s text extraction now
   treats inline phrasing tags as no break and drops `<rt>`/`<rp>`
   (unclosed `<rt>` ends at the next ruby part or `</ruby>`). New packs only;
   readers and the format are unchanged.
4. **`wss refresh` asked for every declaration again** (category, resources,
   arch, license…), although the pack already holds them. It now defaults
   them from the pack's manifest; only the new `--version` is needed.
   Anything given on the command line or in `--recipe` still wins.

## Seen, not changed (reported)

* Audio and video in EPUBs (草枕's MP3s, SMIL overlays) are not carried; that
  is WSS release 2 (transcoding), as `crates/wss-core/NOTES.md` says.
* A PDF's own `Title` is used as the pack name, which for InDesign exports
  is a file name (`Appendix_44_html1.indd`). It is what the source states;
  `--name` overrides it.
* Converting a folder that is a git checkout lists ~30 `.git/` files as
  "not carried" in the report. Harmless noise; a later change could skip
  dot-folders silently.
* A page served as `text/plain` (a raw GitHub file) becomes a pack with no
  search index; `deltd` reports it as skipped (`no_index`). Correct, but a
  capture of a raw file is rarely what someone wants.
* zstd passthrough did not apply to any page tested (dictionary-compressed
  entries are always decoded on the box), as `crates/deltlib/NOTES.md`
  finding 4 already says.
* On the desktop, a search hit's link is the chapter title, which for 草枕
  is a single character (一): a very small click target.
* With `RUST_BACKTRACE=1` in the environment, every `wss` error prints a
  stack trace after the plain message (anyhow's behaviour).
