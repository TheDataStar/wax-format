# DeltOS — Implementability Sweep

Pre-implementation audit of all eight track documents plus the Design Language

*September 2026 · one independent auditor per document · ~140 findings*

## 1. Why This Sweep Is Different From the Earlier Reviews

Every document in this set has already been reviewed twice: once independently, per track, and once holistically across all nine documents (master plan §7). Both passes were looking for contradictions — a statement in one document that a statement in another contradicts. Both found real ones and both were worth doing.

Neither pass could find the defect class that actually stopped work. Three consecutive Track A implementation passes each halted on something no consistency review would have flagged, because nothing in the documents contradicted anything: a header field whose byte order was never stated, a flags field listing four flags and assigning no bit numbers, a manifest value that was self-referential, a field pointing at an identity another section had deleted, a chain of index segments a reader was required to merge with no mechanism for finding them. Each is internally consistent. Each is unbuildable.

This sweep read all nine documents through that lens instead — not "do these agree?" but "could an engineer build this without inventing something?" One auditor per document, no auditor seeing another's document, all working from the same seven-class taxonomy derived from the real Track A failures.

| **Class** | **Defect** | **The real instance it came from** |
|---|---|---|
| A | Undefined value domain | A flags field naming four flags and assigning no bit numbers; a compression column with no permitted values. |
| B | Self-referential or unmaintainable value | total_size_bytes recording an archive's own size from inside that archive, in a table declared immutable. |
| C | Dangling referent | depends_on defined as carrying "pack ids" in the same table whose next note deletes the id field. |
| D | Mechanism named but not mechanized | "The reader merges the segment chain" — with no way to find segments 2..N given a pointer to one. |
| E | Unowned or mis-sequenced dependency | A7 signing tagged P4 while three other tracks assumed it live from P2. |
| F | Internal contradiction | index_offset described as pointing at the base segment and as rewritten on every append. |
| G | Unsatisfiable requirement | A brief requiring both a random UUID per build and byte-identical rebuilds. |

*The taxonomy earned its keep immediately: every class found instances in every document, and class D — the one no consistency review can detect, because an unmechanized assertion contradicts nothing — was the single largest category.*

## 2. The Six Systemic Causes

The useful finding is not 140 defects. It is that they cluster into six causes that repeat in every document, which means the fix is structural rather than 140 individual patches.

- **1. Shared vocabularies have no owning document:** Hardware tier names, Deployment Profile names, role strings, status enums, the MQTT topic grammar, hostname patterns, health-API states, progress event types. Each is defined loosely in whichever document happened to need it first, restated slightly differently in the two or three documents that consume it, and pinned to literal values in none. This single cause produces most of class A and all of class C.
- **2. The two-axis confusion keeps regenerating:** Deployment Profiles (Kiosk/Classroom/Community Hub/Field Ops) and hardware tiers (pi_zero_2w/pi_4/pi_5/mini_pc) are deliberately separate axes, and the master plan's holistic review already caught several places where one was used for the other. It found them and fixed them one at a time — and the sweep found fresh instances in Tracks B, D, E and G. They keep coming back because there is no published mapping between the two axes and no stated ordering within either, so every author has to improvise the relationship each time.
- **3. Hardware budgets are circular and nobody owns them:** Track G never costs the orchestrator and proxy against the Classroom floor. Track H gives no per-service RAM floor for any of its ten services. Track D states no minimum RAM for the tier it puts a local LLM on. All of them defer to Track E's consolidated budget; Track E's §22 states that budget is still open and is waiting for exactly those numbers. Everyone is deferring to everyone.
- **4. Every trust boundary is asserted rather than specified:** The shell's privilege split names five IPC operations with no wire format, no argument types and no error taxonomy. The reverse proxy's forward-auth gate depends on a cookie whose scope is never stated — and on a domain shared with mutually-distrusting pack origins. Identityd's interface is declared closed and narrow, then used for credential verification and profile writes that interface does not contain. The OS update channel has no signature requirement at all. These are the highest-consequence findings in the sweep and they share one shape: the security property is stated as a conclusion, and the mechanism that would produce it is missing.
- **5. Amendments are recorded where they were decided, not where they are owned:** The Design Language document alone claims eight resolutions were landed in Tracks B, C, F and H. Track D records a resolution as "cross-referenced" into a section that contains no such cross-reference. This is precisely the mechanism that produced the Track A/B defects found during implementation — a change agreed in one document and never landing in the document that owns the field.
- **6. "E.g." is doing load-bearing work:** Example values are used where normative ones are required, in places where the example IS the specification: an MQTT ACL topic prefix given as "e.g. deltos/v1/actions/#", a DNS suffix given as "e.g. deltos.lan" and then treated as settled elsewhere, a profile slot range given as "e.g. 0–31" that a port-derivation formula depends on. An implementer cannot ship an "e.g."

## 3. Blocking the Next Prompt — Track B / B1 (zim2wax)

B1 is the next scheduled component and the master plan calls it "the critical-path unlock for every other track's testing." Five findings would have stopped it on contact, in the first hour. This section alone justifies the sweep.

- **[Critical]** **A · Track B §4 —** ZIM paths are namespace-qualified (A/, I/, C/ depending on ZIM version) while intra-article HTML links are relative and namespace-free. Nothing states whether entries.path keeps the prefix, strips it, or whether zim2wax rewrites link targets — and the same unstated convention governs icon, entry_point and redirect_to, which all resolve against entries.path. A wrong guess breaks every internal link in a converted Wikipedia, and the converter cannot be written without picking one.
- **[Critical]** **D · Track B §2/§4 —** Five required manifest fields — name, icon, category, version, min_hw_tier — have no source anywhere in the ZIM mapping table, and ZIM carries no analog for category or min_hw_tier at all. zim2wax must invent values, prompt an operator, or refuse to emit a manifest, and the document does not say which. Note this is downstream of the A2b work: wax-builder now hard-rejects a manifest missing any required field, so zim2wax cannot emit a pack at all until this is answered.
- **[Critical]** **A · Track B §3 —** redirect_to's content is never defined — a target path, a rowid as text, or a URL — while ZIM's own redirect dirents store a target dirent index, so zim2wax must translate into an undefined form. Nor is there any stated behavior for cyclic or dangling redirect chains, which real ZIMs contain.
- **[Critical]** **G · Track B §2/§6/§9 —** The licensing rules cannot all hold. §2 permits license to be free text; §6 has wax-builder refuse to emit any pack whose license is outside a fixed allowlist; §9 has a human moderator review "an unrecognized license." A free-text license is by construction outside the allowlist, so §2 permits a value §6 guarantees can never build, and §9's review path is unreachable. Real Wikipedia ZIMs carry free-text or absent License metadata, so this fails on the flagship content at P1.
- **[Critical]** **A · Track B §6 —** The auto-approve list is written as license families, not SPDX identifiers: "CC-BY", "GPL-family" and "GFDL" are not valid SPDX ids (SPDX requires versions), and "public domain" has no id at all. The matching rule — exact, prefix, family expansion, -or-later handling, compound expressions — must be invented, in a check that ships at P1.
- **[Moderate]** **E · Track B §4/§13 —** zim2wax must write a search_index FTS5 table whose schema, column set, tokenizer selection and text-extraction rules are owned by neither track clearly — A9 is cited as the section, D1/D3 as the owners. Track D's own sweep found the reciprocal gap: D1's merged catalog is scheduled at P1 against a Track A form not standardized until P2.

Two further Track B findings are cheap to fix and worth doing in the same pass: install_state(pack_id, ...) still uses the identity field the schema deleted (it should be archive_uuid, exactly as the packs table was corrected), and the catalog's sha256 never says what it digests — undefined for a multi-volume pack, and the thing F4 verifies a download against.

## 4. Cross-Cutting — Fix Before Any Further Track Starts

These are not per-track defects. Each one invalidates logic in three or more documents, so fixing them in one place is worth more than fixing any ten individual findings.

- **[Critical]** **A · Track E §5 —** The hardware tier table — explicitly "the authoritative source for what each tier's hardware actually is" — states RAM and storage as ranges, not floors. pi_4 is "2–8GB." A pack declaring min_hw_tier: pi_4 may therefore land on a 2GB or an 8GB board, which makes the field useless as a gate and makes Track D's tier-based feature gating undecidable. Every gating decision in Tracks B, C, D and H rests on this table. It needs explicit min_ram / min_storage / arch columns and a stated rule that the floor is what other tracks may assume.
- **[Critical]** **A · Tracks B, D, E, G —** Neither axis has a stated ordering, and there is no published mapping between them. "Classroom tier and above", "Community Hub-tier-and-above" and min_hw_tier comparisons all require a total order that is never written down (is mini_pc above pi_5? is Field Ops above Community Hub?). Track E's own review claims the profile/tier phrasing was swept; the sweep found surviving instances in four documents, including Track E itself.
- **[Critical]** **E · Track E §2/§5 —** The installable-stack path — committed as co-equal with the appliance image, and explicitly targeting a VPS or repurposed desktop — matches none of the four tier names, so every tier-gated decision in three other tracks is undecidable on a deployment path the project has already committed to. Either tiers become capability classes derived from measured hardware with the four boards as presets, or a generic tier row is added with stated floors.
- **[Critical]** **D · Track F §3, Track C §8 —** The progress event schema is a committed cross-track interface with four of its five elements undefined: event_type has no permitted values anywhere, timestamp has no format or clock source (on an appliance that may have no RTC), payload has no size cap or encoding, and pack_id's meaning is defined only "relative to whatever event_source names" — a relation never defined for either source. Track C emits these, Track H's Kolibri bridge writes them, Track C's C8 dashboard reads them. Three components, no shared vocabulary. Worse, progress_events has no primary key or uniqueness constraint, so the Kolibri sync — a poll loop — duplicates every row on any re-run.
- **[Critical]** **E · All documents —** Nine cross-document amendments are recorded only in the document that decided them. The Design Language claims eight landed in Tracks B, C, F and H (guest_accessible in the manifest, the Guest role in the permission model, the C10 language step, the magnifier in C9, the F6 dashboard spec, and more); Track D records one as cross-referenced into a section that contains no such reference. Each is a silent gap of exactly the kind that surfaced mid-build in Track A. These need verifying at the owning document, one by one, before the tracks that depend on them start.

One budget point belongs here rather than under any track: the consolidated hardware budget is circular. Track E is waiting for numbers from Tracks D, G and H; none of those documents states a per-component RAM floor. Someone has to produce the numbers first, and the natural owners are the tracks that know their own components.

## 5. Track C — Shell (23 sections, 22 findings)

The highest concentration of class-D findings in the set, and they cluster on the one decision the document itself calls the thing that has to be made correctly in P0 — the privilege split between the unprivileged shell and the privileged helper.

- **[Critical]** **D · §2 —** The IPC surface is named as "a fixed, versioned set of operations" listing five, with no wire encoding, no argument types, no response shape, no error taxonomy, no socket path, and no definition of what "versioned" means. Neither side of the system's central privilege boundary can be written.
- **[Critical]** **D · §2 —** The shell is a web page in a stock kiosk browser, and browser JavaScript cannot open a Unix socket. The "narrow, purpose-built bridge" that would close that gap is named and never defined, and the document leaves the transport as an unresolved conditional — which determines the entire authentication design (SO_PEERCRED vs Origin plus token). It is not in the open-decisions list.
- **[Critical]** **A · §2 —** The shell's own origin is the load-bearing value in the primary access check and is never defined — the document says where packs live but never what serves the shell, over what scheme, host or port. The per-session capability token has no issuance channel either: a page with no preload bridge cannot receive a startup secret by any mechanism specified.
- **[Critical]** **D · §5 —** No CSP is specified for pack content anywhere, in the section whose whole isolation argument is "iframe+CSP." Without a connect-src restriction a pack's own JS can reach every other pack's and profile's wax-serve instance, the RAG endpoints, and the shelld bridge itself — origin isolation prevents reading another origin's storage, not making requests to it.
- **[Critical]** **A · §5 —** The per-pack origin is "derived from (pack_index, profile_slot)" with no formula, no base port, no slot count (given as "e.g. 0–31"), and pack_index never defined at all — its source, range and stability across reinstall are all unstated, though the storage-wipe rule and the hostname scheme both key off it.
- **[Critical]** **D · §5 —** Origin storage clearing mandates a Chrome DevTools Protocol call, but CDP's default transport is an unauthenticated loopback endpoint — which, with no connect-src policy on packs, would hand any pack full control of the browser. The call also has no IPC operation to travel over.
- **[Critical]** **F · §23 vs §5 —** Guest sessions are stated to leave nothing behind "by design, not by an unfinished feature," but §5 specifies exactly one storage-clearing trigger — slot reuse after profile deletion. Guest is a persistent profile whose slot is never deleted, so its storage persists indefinitely.
- **[Critical]** **D · §5/§8 —** Progress events carry profile_id and pack_id supplied by the pack itself, and nothing requires the shell to derive them from the sending frame's origin — so any pack can attribute progress to another pack and another student. The postMessage schema the shell is said to validate against is never given.

Also found: the "fixed set" of five IPC operations is contradicted by at least five further capabilities the rest of the document requires (pub/sub events, CDP clearing, network config, profile listing, RAG calls); C11's call path is described two incompatible ways in adjacent bullets; wax-serve lifecycle (when instances start, stop, and how many may run on a 512MB board) is unspecified; the P2 migration from port-based to hostname-based origins would orphan every pack's stored data with no stated migration; TTS has the same cross-origin problem reader mode solves, and no solution; and Track C requires four behavioral changes of Track A's wax-serve that are not flagged as amendments Track A owes.

## 6. Track D — Search & Intelligence (16 sections, 17 findings)

- **[Critical]** **D · §2 —** The cross-source merge and ranking rule is never stated, in a service whose entire purpose is merging results from independently-built indexes. FTS5 bm25 scores are corpus-relative and negative, so scores from two partitions are not comparable — every implementer will invent a different normalization.
- **[Critical]** **A/D · §5/§7 —** "Passage" is the unit that gets embedded, retrieved and cited, and it is never defined — no chunk size, no overlap, no boundary rule, no chunk identifier, and no offset in the citation. A citation to a whole entry path cannot locate a passage inside a Wikipedia-sized article, and two implementers chunking differently produce incompatible vector data for the same pack.
- **[Critical]** **B · §5/§3 —** Vector staleness has no answer. Text search inherits last-segment-wins from the container's segment chain; vectors have no equivalent rule, and the embedding pipeline is build-side only, so nothing on a device can recompute them. Semantic retrieval will return vectors for content that no longer exists.
- **[Critical]** **A · §2 —** The merged catalog has no schema. Without defined columns there is no way to delete one pack's rows on removal, map a result back to a pack and path for display and citation, or decide which partition a pack's rows belong in.
- **[Critical]** **F/A · §4 —** The section's own premise is that the tokenizer decision cannot be made twice without the two disagreeing — and it then makes it twice, at build time by an unstated rule and at query time by another, with no mapping from the languages field to tokenizer configs, no stated value domain for that field, and no rule for a multi-language pack.
- **[Critical]** **E · §14 —** P1 requires syncing a merged catalog across multiple installed packs, which needs the standardized embedded-index form Track A does not commit until its own P2. P1 consumes something that does not exist until P2.

Also: the vector store has no defined home between P4 and P5; no model identifier, quantization level or context window is given for either tier, though a phase item asks to "validate the model choice" the document never made; the Classroom tier names Pi 4 without a RAM floor, and a 1GB Pi 4 cannot hold the stated stack; and the searchd wire contract Track C must build against — query syntax, result shape, pagination, errors — is absent.

## 7. Track E — Hardware, OS & Networking (22 sections, 23 findings)

- **[Critical]** **D · §3 —** The update system's rollback trigger is never defined — no statement of what "known-good" means, what detects a failed update, how many failed boots trigger rollback, or whether a booted-but-broken deployment is detected at all. ostree does not roll back on its own; an unconfigured deployment simply keeps booting the broken tree.
- **[Critical]** **D · §3/§4 —** Because /var is shared and never rolled back, a rollback returns old code to data the new code already migrated — the catalog, the progress store and every service volume survive in their post-update form. The document presents this as the guarantee without noticing it is also the hazard, and states no forward-compatibility rule.
- **[Critical]** **D · §3 —** The OS update channel has no trust model at all: nothing states that commits are signed, where the key lives, how it reaches the box, or what happens to an unverifiable commit. The review caught a missing MQTT credential and missed the update channel, which is the higher-value target. There is also no offline update path, in a document that describes sites with no internet access ever.
- **[Critical]** **C · §14 —** Rejecting dnsmasq removed the only candidate that also provided DHCP, and no replacement is named — yet the Wi-Fi AP must hand out addresses, DNS and the captive-portal option to every classroom client, and the diagnostics API is specified to report DHCP state.
- **[Critical]** **D · §6 —** The captive portal must "answer all three OS probes correctly," and correct is the whole question: returning success suppresses the portal window, returning a redirect opens it but leaves the client reporting no internet and possibly switching to cellular. For an offline box whose portal is the destination, the entire two-state machine must be invented.
- **[Critical]** **A · §11 —** The MQTT topic convention is asserted as stable enough for other tracks to subscribe against, and none of its three variables has a defined value domain — no device-class enumeration, no device-id format or uniqueness scope, no metric vocabulary or units — and the payload has no contract at all. No flow author could write a single subscription.
- **[Critical]** **G · §2/§8 —** A single onboarding wizard performs Wi-Fi and AP setup, on a path that explicitly targets a VPS — which has no radio. The wizard cannot run to completion on hardware the document names as supported, and nothing says which steps are conditional.

Also: if the Kiosk-tier OS POC fails, the named fallback has no update mechanism specified while the document still claims A/B rollback as Kiosk baseline; the RTC mitigation is scoped to the profile that does not need it and omitted for the hardware that does; "Advanced" appears as a profile name in no enumeration; and the requirement calculator has no owner, no phase and no definition of what minimum and optimum actually compute.

## 8. Track F — Admin, Identity & Fleet (22 sections, 20 findings)

Good news first, since two other documents were blocked on it: the role vocabulary IS properly specified here. The closed set {admin, teacher, student, guest, none} is fixed, and a nine-row table maps it to exactly the operations Tracks C and E gate on. Those tracks can build against it. Three caveats: none is a lookup sentinel wrongly folded into the storable role set, no default is stated for operations absent from the table (default-deny is implied, never written), and the literal string encoding is never pinned.

- **[Critical]** **D · §3/§5 —** Identityd's interface is declared closed and narrow — "query_role/list_profiles only, never raw profile writes" — and the document then requires credential verification and admin profile writes that this interface does not contain. The bullet titled "the three IPC calls" enumerates two. An implementer must either invent the entire write and auth surface or read password hashes directly, which the same section forbids.
- **[Critical]** **D · §21/§22 —** The passwordless student path specifies a UI gesture, not an authentication mechanism. Nothing states how a tapped profile becomes the active identity that role checks rest on, or what stops a caller supplying any other profile's id — and because list_profiles deliberately omits role, the switch-profile screen cannot tell a student tile from an admin tile. With password_hash nullable and no credential step, tapping a privileged profile is indistinguishable from authenticating as it.
- **[Critical]** **D · §20 —** The provisioning feed Track H's adapters consume has no delivery model: not whether it pushes or is polled, no payload encoding, path or port, no retry for an adapter that is down, no backfill for a service installed after profiles already exist, and no events for rename, role change or deletion.
- **[Critical]** **G · §20 —** That endpoint's stated authentication is the SO_PEERCRED peer-credential check used elsewhere — which is unavailable over TCP from a container in a separate network namespace. There is no peer credential and no local binary to allowlist. The stated mechanism cannot be implemented.
- **[Critical]** **G · §22 —** The admin is said to be able to set guest_accessible, a field inside the signature-verified manifest. An admin cannot change a signed manifest without invalidating the signature, so half this requirement is uncarryable and needs a local override store the document never mentions.
- **[Critical]** **D · §9 —** Identity restore overwrites the database containing the admin profile and session performing the restore. Nothing states whether that admin survives, whether the operator needs the backed-up box's password to log back in, or how restored profile slots reconcile with slots the throwaway setup already consumed.

Also: no recovery path exists if the generated first-boot admin password is lost, which also makes restore unreachable; the backup snapshots live SQLite databases file-by-file with no quiescing, so a restore can silently fail; teacher profile creation is specified through a console the permission table denies teachers; class_or_group carries a security boundary with no defined domain; and the fleet dashboard's own staleness and low-storage thresholds are undefined.

## 9. Track G — Platform Services & Orchestration (13 sections, 19 findings)

Three cross-track dependencies were checked here because other documents assert them. One is partly true, one is underspecified, one is false.

- **[Critical]** **C/F · §3 —** The wildcard certificate Track C depends on does not exist in this document. §3 refers to "the same wildcard internal certificate as above" — nothing above describes one, and the only issuance model stated is the opposite: per-hostname on-demand issuance. Track C is building against a referent that is never defined and that contradicts the model that is.
- **[Critical]** **D · §2 —** Compose healthchecks report status; they do not restart anything, and restart: reacts to process exit, not to an unhealthy verdict — so a hung-but-running container is never restarted by the named mechanism. The document's central self-healing claim has no implementing component, no failure threshold, no backoff and no escalation.
- **[Critical]** **A/F · §3 —** The forward-auth session cookie must be scoped to .deltos.lan to reach the service subdomains — never stated — and .lan is not on the Public Suffix List, so that scope also exposes the admin session cookie to every pack origin, which the same document moves onto the same domain. Pack content could read or fixate admin sessions.
- **[Critical]** **D · §3 —** Nothing constrains how service containers publish ports. With Gitea's and Node-RED's own logins disabled in favor of the proxy gate, any container publishing on the host's LAN interface is an unauthenticated open instance on a network the document itself calls semi-public.
- **[Critical]** **A/F · §3 —** The fleet cache is specified as two incompatible builds at once: response caching requires the cache box to terminate TLS and serve under its own hostname (changing the URL and removing the end-to-end channel to the catalog service), while a forward proxy preserves the channel but cannot cache encrypted bodies at all. The document asserts an outcome compatible with neither. No cache size cap, TTL, invalidation or eviction policy is stated either, for a cache whose objects are multi-GB packs.
- **[Critical]** **D/A · §3 —** Nothing states how a per-pack hostname becomes a live route: packs start and stop at runtime, the proxy needs a config change for each, and the registrar, trigger and de-registration are all unspecified — as are the value domains of the two variables in the hostname pattern.
- **[Critical]** **A · §2 —** The health API Track F must poll has no bind address, port, path, response schema, service-identifier format or authentication, and its health value domain is undefined.

On tier applicability: the document does state G1/G2 apply from Classroom upward, consistently with the others — but never costs a container runtime, a Compose supervisor and Caddy against the Classroom hardware floor, which it never names. The lowest tier running the most load-bearing component in the plan has no stated budget.

## 10. Track H — Applications & Community Services (18 sections, 18 findings)

- **[Critical]** **D/E · §1/§5/§10 —** Service-to-profile isolation is the largest single gap in the document and is not addressed anywhere. Provisioning distinct accounts does not bind a browser session to the active profile: each service is one long-running service at one fixed hostname holding its own cookie session, so a profile switch in the shell leaves the open service session authenticated as the previous profile — exactly the cross-profile leak the identity bridge is said to exist to prevent. Nothing states what a profile switch does to open service sessions, or how a user logs in at all before SSO lands.
- **[Critical]** **G · §2/§15 —** The provisioning event feed cannot provision services that arrive after the profiles do — five services land at P4, by which time every profile was created at P0–P3 and its creation events are long past. A freshly deployed adapter has no way to learn that profiles exist, and no replay depth, retention or acknowledgment is specified.
- **[Critical]** **A/D · §2 —** Deprovisioning acts on "the corresponding account" via a mapping that exists for exactly one of the six adapters. No rule states how a profile becomes a username in the others, so neither deprovision nor role change can locate the account — and Matrix's localpart character constraints cannot be satisfied by an unstated derivation.
- **[Critical]** **C/G · §10 —** The browser IDE is provisioned "via §2" but appears in none of §2's adapters, has no role-table row, and is single-user by design with a shared password and no user-creation API — so neither adapter shape can provision it. Whether there is one container per profile or one shared instance is also unresolved, with materially different resource costs.
- **[Critical]** **C/D · §12 —** The mail service requires a mailbox and address per profile and appears in no adapter list or role table, and no address format is specified — an implementer cannot determine what a profile's email address even is.
- **[Moderate]** **A · §2 —** The provisioning feed carries every profile's initial credential in clear over an endpoint with no stated address, port, authentication or authorization, readable by any container on that network — while the adapters' own credentials were carefully routed through the password vault.

Also: the Kolibri sync bridge has direction and destination settled but no poll interval, no watermark, no idempotency key and no authority rule, so a re-run duplicates every row; the office-suite choice between two products is never actually made though both other either/or choices were; and no per-service RAM or disk floor is given for any of the ten services, while seven of them are committed to land concurrently at P4 on one box.

## 11. Design Language (21 sections, 22 findings)

This document makes an explicit accessibility guarantee — "every color pairing meets or exceeds WCAG AA contrast" — so the sweep computed the ratios rather than taking the claim. Five pairings fail, two of them badly enough to be unusable.

| **Pairing** | **Tokens** | **Computed** | **Verdict** |
|---|---|---|---|
| Dark Error on dark Surface | C24545 on #2A2723 | 2.99:1 | Fails 4.5:1 text AND 3:1 UI — unusable even as a status dot, and Surface is where table rows render. |
| Light Accent on Background | C1622A on #F2EEE6 | 3.60:1 | Fails 4.5:1. This is the primary-action color. |
| White on light Accent fill | FFFFFF on #C1622A | 4.16:1 | Fails. No defined foreground reaches 4.5:1 on the accent fill, in either polarity. |
| Light Success on Background | 4B7B4E on #F2EEE6 | 4.28:1 | Fails 4.5:1 where the status dot carries a text label. |
| Dark Success on Surface | 5C9A60 on #2A2723 | 4.42:1 | Fails 4.5:1, marginally. |

The accent finding is the consequential one: the single component the system designates as the primary action cannot be built to the document's own AA claim in either polarity, because no defined foreground clears 4.5:1 on the accent fill and the accent itself clears neither ground.

- **[Critical]** **A · §4/§12 —** There is no focus-indicator token at all — no color, width, offset or shape — in a shell explicitly specified as keyboard- and switch-accessible. The only candidates fail the 3:1 non-text requirement. This is the single most accessibility-load-bearing visual in the system and an implementer must invent it.
- **[Critical]** **A · §5 and throughout —** There is no spacing scale anywhere in the document: no base unit, no padding, no gutters, no tile dimensions, no dock height, no corner radius, no border width. The type scale gives sizes with no line heights and no numeric weights. Every dimension in the system must be invented.
- **[Critical]** **A · §7/§8/§9 —** No minimum touch-target size is stated anywhere, in a system built entirely around touch on shared devices used by young learners, and no minimum spacing between adjacent targets.
- **[Critical]** **C/F · §6 vs §15 —** The status-icon vocabulary is declared to be "exactly the states named in §15's fleet-status table and nowhere else invented ad hoc" — and then lists five states that do not match §15's four. There is no glyph for Degraded or Offline, and no fleet state for completed or idle. The fleet dashboard cannot be rendered from the icon set.
- **[Critical]** **A/C · §12 vs §4/§5 —** High-contrast mode and large text are shipped accessibility features with no values behind either — there is no high-contrast palette in the token tables, and the type scale is explicitly closed at five sizes with no multiplier or step rule, so "large text" is unspecifiable within it.
- **[Critical]** **E · §21 vs §3/§7 —** Guest content filtering is specified for the launcher grid only, while search runs through a separate endpoint that is never required to honor the flag — so a Guest can search up and open content the grid deliberately hid. Track D is never told it owes this.

Also: the dock — the most-rendered component in the system — has no stated edge, height, item order or overflow rule; the magnifier has no zoom range, invocation or follow rule; no interaction state other than "active" has a value anywhere (no hover, pressed, focus, disabled or loading); the font stack is specified by reference to a moving external target so glyph metrics differ across a fleet; and no motion durations, easing or reduced-motion setting exist.

## 12. Recommended Order of Work

Not everything here blocks the next prompt, and treating 140 findings as one queue would stall the project. The sweep's own severity ordering suggests four tiers.

| **When** | **What** | **Why this order** |
|---|---|---|
| Before B1 | The five Track B blockers (§3 above), plus the two cheap Track B fixes. | B1 is the next prompt and these stop it in the first hour. Small, well-understood, all resolvable from existing material. |
| Before B1 | Tier floors (Track E §5), the profile/tier ordering and mapping, and the progress event schema. | Cross-cutting. B1 must write min_hw_tier into every pack it produces, and cannot do so meaningfully while the tier it names guarantees nothing. |
| Before each track's first prompt | That track's own Critical findings, especially every trust-boundary finding in C, F, G and H. | These are large — Track C's IPC surface is a design session, not an edit — but none is needed until that track is built. Doing them early wastes the work if the design shifts. |
| Continuous | Verify the nine cross-document amendments at their owning documents. | Cheap per item, and each unverified one is a live instance of the exact failure that stopped three Track A passes. |

## 13. The Structural Fix

Fixing 140 findings individually leaves the six causes in §2 intact, and they will regenerate defects in every document written from here. The one that produces the most of them — shared vocabularies with no owning document — has a direct remedy: give them one.

A Cross-Track Contract document would own, as normative values rather than prose descriptions, every vocabulary that more than one track consumes: hardware tier names with guaranteed floors and a total ordering; Deployment Profile names, their ordering, and their mapping onto tiers; role strings and the default-deny rule; the progress event schema; service health states; install and queue states; the MQTT topic grammar and payload envelope; hostname and origin patterns; and the identifier derivations that turn a profile into an account in each service. Every track document then cites it instead of restating it, and a change happens in one place rather than in the three documents that each hold a slightly different copy.

This is not a new design activity. Nearly every value above already exists somewhere in the nine documents, or was recommended concretely by the sweep; the work is collection, reconciliation where two documents disagree, and pinning the handful that genuinely have no value yet. It also gives the implementer one short document to read alongside the track they are building, instead of four long ones.

*The second structural fix is cheaper and equally worth doing: the seven-class taxonomy in §1 becomes the standard pass over any new or substantially revised document, before it is used to write a prompt. It took one auditor per document to find what three implementation passes had been discovering one defect at a time.*
