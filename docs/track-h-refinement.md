# DeltOS — Track H

Applications & Community Services — Technical Refinement

*Working draft · September 2026 · eighth and final of eight per-track refinements, revised after independent technical review (§17) and a cross-track amendment on Guest access (§18)*

## 1. Scope

Track H is the actual application layer people spend most of their time in once the platform underneath (Tracks A-G) exists: an LMS, a media server, cloud storage and office docs, a wiki, chat and calls, a browser IDE, a CMS, and local email. Every one of these ten services runs as a Track G-orchestrated service (Track G §2) behind Track G's ingress (Track G §3) — nothing here invents its own deployment or networking story. The one genuinely new problem this document has to solve, not inherited from Track G, is identity: unlike Track G's own admin-only tools (G3, G6), every Track H service is inherently multi-user, and nothing so far has said how a DeltOS profile becomes an actual, distinguishable account inside Kolibri, Nextcloud, or any of the rest. Settling that once, centrally, is §2's job before any individual service is discussed.

## 2. The Identity Bridge — Provisioning DeltOS Profiles Into Self-Hosted Services

Track G's pattern for its own admin-only tools — gate everyone out behind G2's forward-auth check, run the backend under one shared account (Track G §3) — doesn't fit here. A wiki needs to know who edited what; Kolibri needs distinguishable per-student progress; Nextcloud needs per-user storage and sharing. A different mechanism is needed, and it needs settling once, not reinvented per service.

- **Transport — an added interface on an already-scheduled component, not a new unowned one:** deltos-identityd (Track F §3) is a host-local privileged daemon reached by Unix-socket peer-credential checks — a channel Track G-orchestrated containers (where every Track H service actually runs, §1) can't reach. Rather than assume this crossing away, identityd gains a second, distinct interface for it: a local HTTP endpoint bound to the address G1's compose network can reach, exposing a small provisioning-event feed (new profile, role, deprovision) that each service's own adapter container polls. This is confirmed as an addition to identityd's own document (Track F §20) rather than asserted unilaterally here — and because it's one more interface on a component Track F already lands at P1 (Track F §16), nothing new needs its own phase-table entry: the feed exists as soon as identityd does, well before H1/H5/H6/H8 need it at P3 (§15).
- **Two provisioning shapes, not one — the API adapters actually have:** Kolibri, Nextcloud, and Conduit each expose a genuine admin API this event-driven adapter can call to create an account (Kolibri's user-management REST endpoint, Nextcloud's OCS Provisioning API — POST /ocs/v1.php/cloud/users, which is what actually accepts a quota field at creation, distinct from the occ CLI's own separate user:add/user:setting split, §5 — and Conduit's Matrix registration endpoint). Wiki.js's account creation goes through its GraphQL admin mutation set the same way. DokuWiki (§7) and Grav (§11) have no such API at all — both store accounts as flat files (users.auth.php; individual account YAML files) with no network-reachable admin surface. For those two specifically, the same provisioning event instead drives a local adapter that writes the new account directly into the relevant file, using the same file-locking discipline any concurrent writer to a shared config file needs — a different implementation shape from the four API-backed adapters, sharing only the triggering event, not the same code path.
- **Role mapping, made concrete rather than merely insisted on:** Leaving role mapping to each backend's own default is a real risk worth avoiding (a new account often defaults to that service's own "admin" if nothing else is specified) — but insisting on that without naming the actual mapping just moves the gap to whoever implements this. Settled here:

| **DeltOS role** | **Maps to (Kolibri / Nextcloud / Conduit / Wiki.js)** | **Maps to (DokuWiki / Grav)** |
|---|---|---|
| admin | Facility admin / Admin / Server-admin flag / Administrator group | admin (usermanager group) / admin |
| teacher | Coach / User (with a shared-folder role in H5) / Regular user / Editor group | editor / editor |
| student | Learner / User / Regular user / Contributor group (edit own only, where supported) | user / editor (no finer-grained role available) |
| guest | Not provisioned — see §18's amendment | Not provisioned — see §18's amendment |

- **Two eras, one mechanism early, a better one later — and the Gitea contradiction this corrects:** Before F12/SSO exists (P0-P3, when H1/H5/H6/H8 land, §15), each provisioned account still needs its own password — the provisioning event carries a one-time credential the adapter sets on the new account. Once F12 lands (P4), Nextcloud and Wiki.js can instead auto-provision per-user from Authelia's forward-auth headers on first login, since both keep their own login/session machinery active and simply trust a validated header to fill it — a materially different integration shape from Gitea's, corrected here: Track G's own review settled that Gitea's built-in login is disabled entirely, with every request running under one shared internal service account behind G2's forward-auth gate (Track G §3, §4) — there is no per-user identity inside Gitea to auto-provision, and Gitea is not a Track H service in any case. The earlier draft of this section wrongly listed Gitea alongside Nextcloud/Wiki.js as supporting this; that claim is withdrawn. Matrix's own registration protocol (§8) is not header-based regardless of F12 and keeps using the explicit provisioning event indefinitely, not just as an interim fallback.
- **Credential disclosure — an actual channel, not an assumed one:** F2's password disclosure happens inside deltos-shelld itself, at first boot, before anything else exists (Track F §2) — a different situation from a Track H adapter, running behind G2 and never part of deltos-shell, needing to reach the shell's UI on an ordinary running box, for which no channel previously existed. Resolved the same way C2 already learns about B4 changes without a push channel into the shell (Track C §2): identityd records a pending-disclosure flag per profile when a one-time credential is set; deltos-shell polls for any pending disclosure belonging to the currently active profile and surfaces it as a one-time in-shell notification the next time that profile is actually in use, rather than assuming an inbound-push mechanism into the shell that was never built.
- **Adapter credentials, routed through F13 — not left in local config files:** Each adapter (Kolibri sync, Nextcloud, Conduit, Wiki.js, and the two file-based adapters) necessarily holds a privileged admin credential for its own backend — exactly the class of shared service-account credential Track F's F13 (Vaultwarden) exists to hold (Track F §11). These are machine-retrieved secrets, not a teacher-facing use of the vault, so they don't reopen F13's admin-only scoping question (Track F §15) — each adapter fetches its own credential from F13 via Vaultwarden's own CLI/API at startup rather than keeping it in a local config file no one is tracking.
- **Deprovisioning, stated rather than left as a silent gap:** A profile deleted or archived in F11 (Track F §3) fires the same event in reverse — the adapter disables, not deletes, the corresponding account, preserving Track F's F10 backup/restore integrity (Track F §9) rather than leaving an orphaned login nobody remembers exists.

## 3. Learning Management System (H1) — Kolibri

The master plan's own line for H1 says it "ties directly into C8's coach dashboard" — but Track C's C8 design reads progress exclusively through packs' postMessage bridge (Track C §5, §8), a mechanism built for WAX content packs, not an external self-hosted service. Settling how Kolibri's own progress data actually reaches F11/C8 is this section's real job.

- **A sync bridge, not a shared postMessage channel — pending Kolibri's own API confirmation:** Kolibri runs as its own Track G-orchestrated service at kolibri.deltos.lan behind G2 (Track G §3's hostname convention). This design assumes Kolibri's REST API exposes per-lesson completion data at a granularity fine enough for a periodic sync — plausible given Kolibri's stated purpose, but not yet confirmed against a running instance (§14); if it can't, the fallback is a coarser course-level completion sync rather than abandoning the integration. Assuming it holds: a small adapter, deltos-kolibri-sync, polls that API and writes completion events into F11's progress_events table (Track F §3) using the same shape C8 already reads — profile_id, pack_id, event_type, timestamp, payload — plus a new event_source column (Track F §3's amendment, Track F §20) distinguishing wax_pack rows from kolibri rows, since pack_id itself carries a Kolibri channel/lesson identifier for these rows rather than a WAX archive_uuid and the two id spaces are not interchangeable. C8's dashboard (Track C §8) reads event_source to decide how to resolve and label pack_id before display, rather than assuming every row's pack_id means the same thing.
- **Identity via §2's bridge, with the mapping stored, not implied:** Kolibri accounts are provisioned through §2, not created ad hoc in Kolibri's own admin UI. The resulting Kolibri-user-ID-to-profile_id mapping lives in deltos-kolibri-sync's own small SQLite store under /var/lib/deltos/h1-kolibri-sync/ (Track E §4's convention), which puts it inside Track F's F10 backup boundary (Track F §9) like every other piece of DeltOS state, rather than an unowned mapping nothing backs up or restores.
- **Content, kept separate from progress:** Kolibri's own channel content (video lessons, exercises) is Kolibri-native content imported through Kolibri's own channel format, not converted to WAX — a separate concern from B-track's packs. Track B's B5 starter-pack proposal already references "age-appropriate Kolibri channels" as something offered alongside WAX packs, not instead of them (Track B §7); this document doesn't change that division.

## 4. Media Server (H2) — Jellyfin

A Jellyfin-based library server for attached-storage video/music — the most straightforward Track H service, and not coincidentally the one the master plan tags earliest, P2, landing alongside Track G's own now-corrected G1/G2 (Track G §2, §11).

- **Storage, matching Track E's add-on philosophy:** Jellyfin's library lives on whatever external/expansion storage the admin has attached (Track E §21's Decision 3 — hardware add-ons as a general principle, not a cataloged accessory list) rather than under /var/lib/deltos itself. A media library can run to hundreds of gigabytes and has no reason to share Track F's F10 backup boundary (Track F §9) — losing it to a hardware swap is recoverable by re-attaching the same drive, unlike F11's progress data.
- **Identity bridge available, not mandatory:** Jellyfin's multi-user accounts are lower-stakes than the rest of this document — no grading, no shared documents, no personal data beyond watch history — so §2's provisioning bridge is available but not required for H2 specifically. A single shared library account is an acceptable v1 default; per-profile accounts via §2 are an option an admin can turn on.

## 5. Cloud Storage & Content Sharing (H5) — Nextcloud

Nextcloud, per the master plan — and the one Track H service structurally load-bearing enough that H3 (§6) is described as "integrated with H5," not standing alone.

- **Identity, mandatory here:** Unlike H2, Nextcloud's whole value is per-user storage and sharing — §2's identity bridge is mandatory for H5, not optional, since a shared account would mean every profile sees every other profile's files at cloud.deltos.lan.
- **Storage quota, tied to the calculator's own numbers:** Each provisioned Nextcloud account gets a default storage quota set at creation via the OCS Provisioning API's own quota field (§2) — a conservative default at Classroom scale, admin-adjustable at Community Hub scale where more storage is typically attached, rather than one arbitrary number applied everywhere. The figures themselves come from the same per-tool resource-cost thinking behind Track B's calculator work (Track B §17, Track C §7's amendment).

## 6. Browser Office Suite (H3) — Collabora / OnlyOffice

Integrated with H5, per the master plan — meaning H3 has no independent identity or storage story of its own.

- **No separate accounts — rides on H5's:** Collabora/OnlyOffice Docs edits files that live in Nextcloud (§5); it authenticates a document-editing session through Nextcloud's own WOPI-like integration, not a second account created via §2's bridge. H3 has nothing to provision independently — it's a capability H5 gains, not a tenth thing needing its own identity story.
- **Phase dependency, stated plainly:** H5 is tagged P3 and H3 is tagged P4 in the master plan — consistent with H3 depending on H5 rather than the reverse, and worth confirming here so H3's own P4 tag isn't read as independent of H5's prior existence (§15).

## 7. Wiki (H6) — Wiki.js / DokuWiki

Sized to hardware tier, per the master plan — worth naming which of the two options applies where, since the master plan lists both without picking.

- **Tier-scoped choice:** DokuWiki (flat-file, no database) on Classroom-tier hardware, matching the project's own SQLite-or-flat-file service-selection filter used since the earliest tracks; Wiki.js (Node.js, needs its own database backend and more RAM) on Community Hub tier, where its richer editing/versioning UI is worth the larger footprint. Both are reached at wiki.deltos.lan and provisioned through §2's identity bridge for edit attribution — a wiki with no identity behind an edit is missing the one thing that makes "who changed this" meaningful. The two lean on different halves of §2's bridge: Wiki.js is provisioned through the API-based shape (its own GraphQL admin mutations), while DokuWiki — flat-file and API-less by design — is provisioned through the file-based shape (a direct write to its users.auth.php), the same mechanism §11 uses for Grav.

## 8. Secure Chat & Collaboration (H8) — Matrix / Conduit

Conduit over Synapse specifically for this hardware range, per the master plan — matching the project's single-binary, Rust-native service-selection filter used everywhere else.

- **Identity, Matrix's own protocol — not header-based:** Matrix's registration/login flow is its own protocol, not a simple reverse-proxy-header scheme, so §2's provisioning bridge calls Conduit's own registration API directly rather than relying on F12's forward-auth headers even after F12 lands — the stated exception to §2's general "F12 takes over" pattern. Matrix accounts at chat.deltos.lan are provisioned explicitly, on every DeltOS install, indefinitely.
- **Federation, off by default:** Matrix's protocol supports federating with the wider Matrix network; DeltOS's Conduit instance ships with federation disabled by default via Conduit's own allow_federation configuration key set to false at first boot — a config-file setting Conduit itself enforces at the protocol layer, not a claim borrowed from another track. (Track D §9's federated-search/RAG trust-boundary discussion is a separate, analogous decision about a different subsystem — worth noting as the same underlying instinct, but not the mechanism doing the enforcing here.) A school's chat server shouldn't be reachable from the public Matrix network unless an admin deliberately flips that key.

## 9. VoIP / Voice & Video (H10) — Element Call + coturn

Built on H8's Matrix stack rather than a separate Asterisk deployment, per the master plan — meaning H10 has essentially the same identity story as H8 and no independent one of its own.

- **coturn's own footprint, flagged rather than assumed free:** coturn (the TURN/STUN relay Element Call needs for calls between devices behind different NATs) is the one component here with a real, distinct hardware/network footprint — worth adding to Track E's still-open Community Hub tier budget concern (Track E §5, §17, §22) alongside Track F and Track G's own daemons, rather than assumed free just because it rides on H8's identity story.

## 10. Browser IDE (H4) — code-server

VS Code in the browser, per the master plan — a single-profile-scoped tool, not a shared or collaborative one like H5/H6/H8.

- **Per-profile workspace, no sharing model needed:** Each provisioned code-server instance (via §2) at code.deltos.lan gets its own workspace directory under that profile's own storage, mirroring H5's per-user model (§5) rather than inventing a third storage convention. There is no cross-profile sharing surface to design here, unlike H5, H6, or H8.

## 11. Publishing / CMS (H7) — Grav / WordPress

Grav on constrained hardware, WordPress at Community Hub tier — a genuine tier split, unlike H6's, worth naming why.

- **Why the split, stated:** Grav's flat-file, no-database model fits the same SQLite-or-flat-file consistency filter as DokuWiki (§7) and needs meaningfully less RAM than WordPress's PHP-plus-database stack — a real, not arbitrary, tier boundary rather than an unexplained option list. Both are reached at blog.deltos.lan and provisioned through §2's identity bridge for author attribution — Grav through the same file-based adapter shape as DokuWiki (a direct write to its account YAML files, no admin API to call), WordPress through the API-based shape (its own REST API's user-creation endpoint), consistent with the tier split putting a file-based, API-less service on the constrained tier and an API-bearing one on Community Hub.

## 12. Email Server & Webmail (H9) — Maddy + Roundcube

Scoped to the local network, per the master plan — worth being explicit about what that scoping actually rules out.

- **Local-network mail, not internet email:** Maddy handles mail between DeltOS profiles on the same box or fleet (deltos.lan addresses, matching Track G's G2 hostname convention, at mail.deltos.lan for Roundcube's webmail) — it is not configured to send or receive internet email, which would require a public MX record, a public IP, and DNS this box's whole design doesn't provide (Track E's E10 CoreDNS zone is explicitly scoped to a non-internet-resolvable suffix, Track E §14). This is a deliberate scope boundary worth stating plainly, since "email server" without qualification usually implies internet mail — and an SMTP server left to its defaults will still attempt internet delivery for any address outside its own domain, so the boundary needs enforcing, not just declaring.
- **Enforced, not just configured:** The concrete control, applied at first boot rather than left to the admin to remember: Maddy's own recipient-domain check is restricted to deltos.lan (and any additional fleet domains registered through F6), so a message addressed outside that set is rejected at the SMTP layer with a clear bounce rather than queued for outbound delivery — this is an enforcement Maddy itself carries out, not a claim resting on another track's design. A second, belt-and-suspenders layer — blocking outbound port 25 at the network level, so even a misconfigured Maddy instance can't reach the public internet — would need a general outbound-firewall posture that no track currently defines; flagged here as a hardening item for whichever track ends up owning host-level network policy (§14), rather than asserted as already in place.

## 13. Hardware & Profile Scoping

- H2 (media server) is the one Track H service viable even at Classroom profile, matching its own P2 tag (Track G §2, §11) — everything else here assumes at least Classroom-scale admin/teacher structure (H1, H6) or Community Hub-scale resources (H3, H4, H5, H7, H8, H9, H10).
- H3, H4, H5, H7, H8, H9, and H10 are realistically Community Hub-tier services — Track E's mini_pc floor (Track E §5) is what makes running several of these concurrently plausible at all, and Track E's own still-open consolidated budget (Track E §22) needs every one of them added as they're actually deployed, not assumed to fit by default.
- §2's identity bridge applies wherever any Track H service is provisioned at all — it isn't itself tier-scoped, since even a single Classroom-tier Kolibri deployment (H1) needs it.

- Verify Kolibri's REST API surface actually exposes per-lesson completion data at the granularity §3 wants — §3 now states this assumption openly and gives a fallback (coarser course-level sync) if it doesn't hold, so this item is a verification task against a running instance, not an unresolved design gap.
- The provisioning event's schema (§2) is now settled jointly with Track F — deltos-identityd's new provisioning endpoint and the progress_events.event_source column are confirmed in Track F §20. What remains open is narrower: the exact per-adapter field shapes (what Nextcloud's OCS call needs versus what Conduit's registration API needs) still need working out against each service's real API, not the schema's existence or its transport.
- Settle a concrete storage-quota default for H5 (§5) once Track B's calculator (Track B §17, Track C §7's amendment) has real per-tool figures to draw from, rather than the placeholder reasoning given here.
- Decide whether H9's Maddy instance should support any inter-box mail once Track F's F6 fleet pairing exists (Track F §7) — this document scopes H9 to one box's own profiles only, but a paired fleet might reasonably want mail between boxes too.
- Confirm coturn's resource footprint (§9) actually gets folded into Track E's Community Hub budget item (Track E §22) rather than left as a one-line flag here.
- No track currently owns a general outbound-firewall/egress-policy posture for the box as a whole; §12's port-25 block is one instance of a need that will recur (e.g. any other service that could reach the public internet by default). Worth raising with Track E as a candidate for a general hardening section rather than solved piecemeal per-service.
- Confirm the exact file formats §2's file-based adapters need to write — DokuWiki's users.auth.php line format and Grav's account YAML schema (§7, §11) — against each service's actual current version, since both are undocumented-but-stable conventions rather than versioned APIs.

## 17. Independent Review — Findings and Resolutions

- **[Critical]** §2 claimed Gitea supports per-user auto-provisioning from Authelia headers "natively," directly contradicting Track G's own settled design, in which Gitea's built-in login is disabled and it runs behind G2 under one shared internal service account — the opposite of a per-user auto-provisioned identity. Resolved: Gitea removed from the auto-provisioning list; §2's "two eras" bullet now names Gitea's shared-account shape as the deliberate exception it is, not an oversight (§2).
- **[Critical]** §2's API-based provisioning mechanism was silently extended by implication to DokuWiki (§7) and Grav (§11), neither of which exposes a network-reachable admin API — both are flat-file-backed by design. Resolved: a distinct file-based adapter shape added to §2 (a direct write to each service's own account file — users.auth.php for DokuWiki, YAML for Grav), sharing only the triggering provisioning event with the API-based adapters; §7 and §11 each updated to name which shape they use (§2, §7, §11).
- **[Critical]** §3 silently overloaded Track F's progress_events.pack_id column with two incompatible ID namespaces — a WAX archive_uuid and a Kolibri lesson ID — with no discriminator between them, and without the backward-flowing confirmation every other cross-track schema change in this project has received. Resolved: a new event_source column added to the concept, distinguishing wax_pack rows from kolibri rows, confirmed in a companion amendment to Track F (§3, Track F §20).
- **[Critical]** The Identity Bridge (§2) — this document's own central new mechanism — had no owner, no phase-table line, and no confirmed transport, despite H1, H5, H6, and H8 all depending on it by P3. Resolved: reframed as a new interface (a local HTTP provisioning-event endpoint) added to deltos-identityd, a component Track F already schedules at P1 — meaning no new phase-table line is needed, since the capability rides on an already-committed component's own schedule, confirmed in Track F §20 (§2).
- **[Security]** The "shown once, in-shell" credential-disclosure claim named no actual channel by which a Track H service — running behind G2, outside deltos-shell's own process — could push a message into the shell's UI. Resolved: redesigned as a poll-based mechanism (identityd records a pending-disclosure flag; deltos-shell polls and clears it), modeled on the same pattern Track C's shell already uses to learn of B4 catalog changes (§2).
- **[Security]** Provisioning-adapter credentials — the admin-API credentials each adapter needs to reach Kolibri, Nextcloud, Conduit, and Wiki.js's own admin surfaces — had no stated storage or custody model. Resolved: routed through Track F's F13 (Vaultwarden) as machine-retrieved secrets, explicitly distinguished from F13's teacher-facing vault use so this doesn't reopen F13's admin-only scoping question (§2).
- **[Security]** H9's "local-network mail only" scoping was stated as a configuration intention rather than an enforced boundary — an SMTP server left to its defaults will still attempt internet delivery for any address outside its own domain. Resolved: Maddy's own recipient-domain check restricted to deltos.lan and registered fleet domains, rejecting anything else at the SMTP layer; a network-level egress block flagged forward as a hardening item no track currently owns (§12, §14).
- **[Moderate]** §8's federation-off-by-default claim cited Track D §9 as its authority, but Track D §9 is actually about federated-search/RAG trust boundaries — a different subsystem entirely — making the citation an analogy dressed as a settled cross-track policy. Resolved: re-grounded in Conduit's own allow_federation configuration key, the actual mechanism doing the enforcing, with Track D §9 kept only as a noted parallel, not a cited authority (§8).
- **[Moderate]** §2's account-sprawl-risk bullet cited Track F §11 as its authority, but Track F §11 is F13's password-vault scoping discussion, not backend-service default-admin-role sprawl — a miscitation. Resolved: dropped in the rewrite; the new role-mapping table (§2) makes the underlying point without relying on that citation (§2).
- **[Moderate]** §3's body text stated Kolibri's per-lesson API granularity with more confidence than the hedge already present in §14 warranted, with no fallback given if the assumption doesn't hold. Resolved: the assumption stated visibly alongside an explicit fallback — coarser course-level sync — if per-lesson data isn't exposed (§3).
- **[Moderate]** §2's "closest-matching role" claim for provisioned accounts had no concrete mapping backing it. Resolved: a role-mapping table added, naming DeltOS admin/teacher/student against each service's own role vocabulary (§2).
- **[Moderate]** The Kolibri-user-ID-to-profile_id mapping §3 depends on had no stated storage location or backup ownership. Resolved: specified as its own SQLite store under deltos-kolibri-sync's data directory, inside Track F's F10 backup boundary (§3).
- **[Minor]** §2 and §5 both described Nextcloud quota-at-creation via "occ user:add/API," conflating the occ CLI (no quota-at-creation support) with the OCS Provisioning API (which does). Resolved: both references corrected to name the OCS Provisioning API specifically (§2, §5).
- **[Minor]** §2 described the "F12 headers" provisioning pattern identically for Gitea/Node-RED (shared account, own login disabled) and Nextcloud/Wiki.js (per-user auto-provisioned, own login active) without distinguishing two materially different integration shapes. Resolved: the rewritten §2 states plainly that Nextcloud/Wiki.js keep their own login machinery active and trust a validated header, a different shape from Gitea's disabled-login pattern (§2).

## 18. Amendment (per product direction on Guest access)

Track F's own companion amendment (Track F §22) adds a fourth role, guest, for a single shared profile an admin may opt into — the product owner's resolution to the walk-in-visitor question this document's own §14 had left open. This section confirms what that means for the Identity Bridge specifically, closing §2's new table row above.

- **Guest is never provisioned into any backend service, by design rather than oversight:** Every adapter this document specifies (§2) exists to give a real, distinguishable person a real account in Kolibri, Nextcloud, Conduit, or Wiki.js — that's the entire point of settling role mapping in §2's table. Guest is the opposite case: one shared, anonymous, admin-toggleable identity with no persistent per-visitor state anywhere in the system (Track F §22). Provisioning it into these services would create exactly one "Guest" account per service that every walk-in visitor shares — an unaccountable shared credential this project's own F13/F3 design has otherwise gone out of its way to avoid (Track F §11, §3). The identity-bridge provisioning event (§2) simply never fires for a profile with role guest; no adapter, API-based or file-based, ever sees it.
- **What a Guest gets instead:** Content-pack browsing only, filtered to manifest-declared guest_accessible packs (Track B §2, Track C §23) — none of H1/H5/H6/H8's own multi-user services are reachable by a Guest profile at all, the same way they're invisible to a Kiosk-tier device with no identity system running (§13). This is a narrower posture than Student, not an equal-but-different one: Student gets a real, tracked identity inside every one of these services; Guest gets none.
